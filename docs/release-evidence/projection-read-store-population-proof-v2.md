# Projection Read-Store Population Proof v2

**Result:** pass

The production named projection route is `conversation/conversation-read-model`. It materializes the existing event contract through the shared decoder, persists to configured store `statestore`, and reports completion only after both tenant-scoped keys are durable:

- `projection:conversations:{base64url(tenantId)}:{base64url(conversationId)}`
- `projection:conversations-index:{base64url(tenantId)}`

The production-boundary live fixture dispatched through EventStore's discovered named handler into the configured read-model store, then queried through the real Conversations detail/list services. Accepted and stable duplicate delivery converged to one detail and one index row at event position 1. A second-write failure was retryable and both queries stayed non-current until retry completed. Unavailable storage produced a bounded indeterminate result; tenant-mismatched input failed without writes or leakage.

After the detail, tenant-index, and dispatch-ledger keys were conditionally erased, detail/list queries did not backfill at query time. EventStore full replay executed the handler's side-effect-free three-operation coordinated plan, restored all three exact keys, and produced current query results equivalent to the pre-deletion results.

**Disclosure — what `Current` means after erasure.** With every derived key for the tenant erased, the list query reports `Current` with zero rows, not `Rebuilding` or `Unavailable`: `AggregateFreshness` over an empty summary set returns `Current`. Destroyed state is therefore indistinguishable from a tenant that never had a conversation. This was evaluated in pass 10 and could not be closed at this seam — `IReadModelStore` exposes only get/save/try-save and `IReadModelBulkStore` only `GetManyAsync(keys)`, so a tenant's surviving detail keys can only be enumerated from the index itself, the very key whose absence is being diagnosed. Closing it needs a durable tenant-index write at first use, which is outside Story 6.2.

**Disclosure — replay does not reproduce timestamps.** `queryResultsEquivalentToPreDeletion` is asserted with `occurredAt` compared *structurally* (present/absent, count, and order), not by exact instant. `ConversationProjectionMaterializer` computes `builder.LastAppliedTimestamp ?? projectionGeneratedAt` and stamps wall-clock time when applied events carry no usable timestamp; participant and file-reference `occurredAt` then resolve as `OccurredAt ?? freshness.LastAppliedEventTimestamp`, so the instability reaches fields the projection contract documents as domain content. A dropped, added, duplicated, or reordered item still fails the assertion; an item dropped and restored with a different timestamp would not. The gap is pinned by `AssertKnownTimestampReproductionGap`, which goes red when production is fixed.

## Gateway production boundary (ADR 0003 Verification 1-2)

Story 6.2 task T2 offered two closures for the production-boundary question: strengthen the fixture, or record a named-owner justification narrowing ADR 0003's own verification wording. **Jerome chose to strengthen the fixture**, so nothing in ADR 0003 Verification 1-2 is narrowed, waived, or carried as a residual gap.

`ConversationProjectionGatewayDispatchLiveTests` drives delivery through `IProjectionUpdateOrchestrator` against a real `daprd` sidecar with a Redis-backed `statestore` component, not through an in-process dispatcher call and not against an in-memory fake. The lane verifies the live sidecar metadata reports a `state.redis` `statestore` with the `ACTOR` capability. It also asserts that the configured `IReadModelStore` is `DaprReadModelStore`, the projection refresh interval is `0`, and the gateway discovered the `conversation-read-model` route from the domain service's operational-index metadata. Structured host logs from the passing run contain both `ProjectionUpdateOrchestrator` and `NamedProjectionDispatchCoordinator` categories, observing the gateway-side stages rather than assuming them.

An accepted append persisted both tenant-scoped keys on one agreeing generation and the production detail/list queries returned `Current`. A duplicate delivery left persisted state unchanged and the tenant index at exactly one row. Missing DAPR/Redis prerequisites and startup failures now fail the mandatory fixture; the recorded run passed 2/2 with **0 skipped**.

The mandatory Aspire runtime-boundary test reached healthy `eventstore` and `conversations` resources, submitted a real `CreateConversation` through EventStore, and observed `Completed` with the expected aggregate id and a non-zero event count. It then polls the production `/query` seam until the projected read model is queryable, so the lane now proves the cross-app named-dispatch path end to end rather than stopping at command status.

**Disclosure — substitutions inside that lane.** Three things in it are harness scaffolding, not production behaviour, and are stated here rather than left in test comments. (1) The delivery-writer-protocol cutover is activated through the production admin endpoint using a locally minted `global_admin` token signed with the disclosed dev key, with Keycloak disabled. (2) Tenant access is seeded by POSTing synthetic `Hexalith.Tenants.Contracts.Events` envelopes to `/tenants/events` rather than by running Tenants; that step asserts only HTTP 200, which the subscription endpoint also returns for skipped and invalid-payload outcomes, so a seeding regression surfaces as a downstream timeout rather than naming itself. (3) The assertion runs against the module's own `/query` seam because gateway handler-query routing lacks a `DomainServiceOptions` registration for the conversations domain. This lane is **not** among the bound `runArtifacts` below; its result is reported in the verification summary only. This lane exposed and corrected the former topology mismatch between the plural Aspire resource name `conversations` and EventStore's canonical DAPR service-invocation app id `conversation`. The deterministic topology suite passes 8/8 and pins those distinct identities.

**Disclosure — single-replica deployment constraint.** The tenant access projection resolves to the platform default `InMemoryTenantProjectionStore`; Conversations registers no durable replacement. The projection is therefore per-replica and lost on restart, and DAPR does not redeliver acknowledged events. Any restart, or a second replica, leaves that instance's projection empty for every pre-existing tenant — and because tenant admission fails closed, the symptom is denial of legitimate callers rather than an error. Conversations is single-replica-only until the deferred durable tenant access projection lands. Every measurement in this artifact was taken single-instance, so nothing here is invalidated by the constraint; it bounds deployment, not the proof.
