## What Went Well

Amelia (Developer): "The observability stories layered cleanly. 6.1 set the meter, counter-naming, structured-log, and `None`-class-guard conventions, and 6.2 and 6.3 extended the same `Hexalith.Conversations` meter without forking a second `IMeterFactory` instance. The contract stories 6.4–6.6 then reused one fixed shape — vocabulary record, JSON converter, entry record, validator, conformance suite — so each was predictable to build and review."

Winston (System Architect): "The safety-by-construction discipline held. Every telemetry dimension value is a closed-vocabulary enum name; no `TenantId`, `PartyId`, `ConversationId`, raw error codes, or `DenialReason.ToString()` reach metrics or logs. Forbidden projection state collapses to Unavailable so observability does not become a tenant-existence side channel. The responsibility-boundary document was held to documenting only what exists and explicitly does not claim ownership of EventStore, Tenants, Parties, Folders, FrontComposer, or provider authority."

Murat (Test Architect): "Story-level evidence grew monotonically across the epic — from 1279 solution tests before 6.1 to 1482 after 6.7 — and each story added focused negative tests (None-class guards, content-safety scans, no-sentinel-leak serialization checks) rather than relying on one final run. The conformance suites give CI-suitable, machine-readable, content-safe output."

John (Product Manager): "Operational and lifecycle value stayed visible and was not rewritten into generic 'add metrics' tasks. Operators get safe rejection/denial/freshness/conformance signals; product owners get release-scope, buyer-acceptance, and second-adopter governance with enforced traceability; buyers and adopters get a formal boundary document. The lifecycle stories also correctly encode the readiness-gate reality that there is no named second adopter yet."

Key strengths:

- Strong story-to-story continuity: 6.1's observability conventions and 6.4's contract-story shape were reused verbatim by later stories, reducing drift and review friction.
- Backward-compatible wiring: telemetry was injected as optional constructor parameters with null defaults, so 428 pre-existing Server tests were never broken when observability was added to hot paths.
- Content-safety treated as a first-class invariant: the 31-term UnsafeTerms blocklist was applied to log templates, dimension values, fixture scenario text, and the boundary document's free text.
- Validators enforce that governance gaps cannot be hidden: deferred substrate capabilities must name consequences, blockers must name approvers, waivers must link, and disqualified adopters must carry rationale.
- Review loops were efficient: most stories cleaned in a single review cycle, with findings auto-fixed and the suite re-run.

## Challenges And Friction

Amelia (Developer): "The recurring friction was content-safety string hygiene, not feature logic. The UnsafeTerms blocklist trips on substrings — `"store"` inside 'data store', `"sequence"` inside 'consequence', `"exception"`, `"unknown"`, and hyphenated `"tenant-"`/`"conversation-"`. Scenario IDs, `SafeMessage` text, and even a conformance-telemetry log test using the `tenant-isolation` gate ID all had to be reworded to pass."

Winston (System Architect): "There were two structural constraints worth recording. The `Hexalith.Conversations.Testing` project cannot reference `Server`, so the 6.3 conformance-status fixture had to live in `Conformance.Tests` rather than `Testing/Fixtures`. And `ConversationPublicationMapper` is static, so 6.2 had to introduce a non-static `ConversationPublicationService` wrapper rather than modify the mapper — telemetry was wired at the service boundary, not inside the mapper or materializer."

Murat (Test Architect): "The largest friction is the one not visible in the seven delivered stories: the two validation stories were never started. 6.8A (telemetry redaction validation) and 6.8B (telemetry cardinality gates) are precisely the independent, fixture-driven proofs that the observability signals are safe under adversarial and high-cardinality inputs. Their `Ready for Dev Preconditions` — approved redaction rules, approved dimension sets, maximum-cardinality expectations, fixture sets, evidence outputs, pass/fail gates, owner, and review date — appear never to have been recorded, which is consistent with the stories remaining in backlog."

Recurring challenges:

- Content-safety substring collisions repeatedly forced rewording of identifiers and descriptions; this was the most common per-story friction and surfaced in the build-process learnings as well.
- Some conformance manifest entries use `releaseGateId: null` because their gate tokens (`conformance-status`, `release-scope`, `buyer-acceptance`, `second-adopter`) are not in the current closed `ReleaseGateId` vocabulary — traceability is by requirement and evidence handle, not by a typed gate.
- Telemetry was deliberately wired as optional/null-defaulted and fire-and-forget to stay off the critical path; this is safe but means production code paths can run with telemetry absent, and absence is not itself observable.
- The build was executed on a constrained host: tmux-win32 encoding bugs blocked the monitor early, the codex worker was unreliable on this host, and create/dev were switched to Claude for Epics 5–6 (recorded in `learnings.md`). This is process friction, not product defect, but it shaped how the epic was driven.

## Key Lessons

1. Observability vocabulary must be designed once and extended, not reinvented per story.

   Story 6.1 deliberately set stable dimension names because 6.2 and 6.3 would extend them. Sharing a single `Hexalith.Conversations` meter and one `None`-class-guard convention across three telemetry interfaces kept the operational surface coherent and made each later story a mechanical extension.

2. Safe-by-construction is necessary but is not the same as proven-safe.

   Every Epic 6 signal is bounded to closed-vocabulary enum names by design, and story-level tests assert no forbidden fields appear. But the dedicated adversarial validation of redaction and cardinality (6.8A/6.8B) was not delivered, so the safety is currently established by construction and per-story unit tests, not by an independent validation gate.

3. Governance records should make omission a validation failure, not a silent default.

   The 6.4–6.6 validators encode this directly: a deferred substrate capability with no named consequences, a blocker with no approver, a waiver with no link, a qualified adopter with no downgrade trigger, and a disqualified adopter with no rationale all produce explicit error tokens. "No silent acceptance of release-blocking unknowns" is enforced by code, not convention.

4. Content non-disclosure is a substring problem, not just a field problem.

   The repeated friction was not leaking a whole `TenantId` field; it was incidental substrings (`store`, `sequence`, `exception`, `unknown`, hyphenated entity prefixes) appearing in scenario text, log templates, and gate IDs. Safe observability requires scanning free text and dimension values, not only excluding known identifier fields.

5. Documentation that defines boundaries must document reality and refuse false ownership.

   Story 6.7 succeeded by documenting only existing behavior and explicitly stating, per adjacent system, who owns the boundary, where truth lives, what fails closed, what evidence Conversations owns versus inherits, and how responsibility hands off — without implying Conversations owns EventStore, Tenants, Parties, legal-hold, attachment, or identity authority.

## Deferred Work And Technical Debt

The most important deferred items are not treated as blame. They are recorded decisions about scope and sequencing. For Epic 6 the single most consequential item is the unbuilt 6.8 validation pair.

Pending validation work — the Epic 6 gap (highest priority):

- `6-8a-validate-operational-telemetry-redaction` was never built (`backlog`). This story is the independent validation that metrics, logs, traces, diagnostics, dashboards, and evidence summaries redact unsafe values — conversation content, user free text, raw business-record identifiers, prompt/content fragments, unbounded error strings, provider payloads, redacted content, unauthorized identifiers, conversation-existence signals, and cross-tenant Party detail — and that any tenant ID appears only where privacy/governance policy approves it. Without it, redaction safety for the 6.1–6.3 signals rests on construction and per-story tests only.
- `6-8b-validate-operational-telemetry-cardinality-gates` was never built (`backlog`). This story is the independent validation that telemetry dimensions stay bounded and approved, that raw IDs/business references/fragments/unbounded external identifiers are rejected as dimensions unless approved for a named surface, and that a story cannot close if telemetry creates uncontrolled cardinality, leakage risk, or incident-noise amplification without an approved waiver.
- The `Story 6.8 assignment plan` readiness gate is `decided`: split 6.8 into 6.8A and 6.8B by default. The split exists; the work behind it does not. The per-story `Ready for Dev Preconditions` (approved redaction rules, approved dimension set, maximum-cardinality expectations, fixture set, evidence output, pass/fail gate, owner, review date) do not appear recorded — these must be authored before validation can begin.
- Carry-forward link: Epic 1's retrospective deferred "some tenant denial timing side-channel work … to hardening/observability work." That timing side-channel — cross-tenant existence/membership probing via response latency, also recorded in `deferred-work.md` (Story 1.5 review) — is an observability/hardening concern that Epic 6's signal-classification work did not address and that 6.8A/6.8B do not own either. It remains open.

Process/status debt:

- `epic-6` remains `in-progress` in sprint status even though Stories 6.1–6.7 are `done`; it cannot move to `done` while 6.8A/6.8B are `backlog`.
- Optional epic retrospectives for Epics 2–6 were skipped during the automated run (per `learnings.md`); only Epic 1's existed before this document. This Epic 6 retrospective is itself `optional` in sprint status.
- Several story file lists note that unrelated working-tree changes (story-automator skill, codex config, gitignore) were present but out of story scope.

Contract and traceability debt:

- Multiple conformance manifest entries (6.3–6.7) carry `releaseGateId: null` because their gate tokens are not in the closed `ReleaseGateId` vocabulary. Traceability is via requirement ID and evidence handle. A later pass should decide whether these gates should be promoted into the closed vocabulary or remain handle-only.
- Reserved-but-unexercised vocabulary values exist (e.g., `PartiallyRebuilt` freshness class, `DeadLettered`/`ReplayRequired` publication-failure classes) because the v1 runtime does not yet emit them; they await the pub/sub and partial-rebuild paths.

Runtime and production-hardening debt (carried forward from earlier epics, still open at program close):

- Idempotency executor wiring remains complete only for add-participant; `EventStoreCommandStatusIdempotencyBridge` is a primitive not consulted by any executor (deferred-work.md, Story 1.6). The bridge's expected owner was named as Story 1.10 or 5.6; neither claimed it.
- Projection accumulator deduplicates by `EventId` only; same-EventId/different-payload poisoning is deferred to production read-model hardening.
- Query list handling enumerates an in-memory tenant set before paging; offset pagination is unstable under concurrent mutation; production push-down and keyset pagination remain deferred.
- `ProviderCorrelationMetadata.ExtensionData` and related dictionaries still need bounded-size/key enforcement.

Release-evidence debt:

- Module-level conformance evidence is unsigned local/CI evidence. Signed release-gate aggregation, manifest signing, and platform-vs-module evidence separation proofs (Story 5.11 framework) remain to be exercised as a release-certification step, not just authored.

## Team Agreements

- Keep observability safe-by-construction (closed-vocabulary dimensions, content-safe log templates, fire-and-forget off the hot path) AND prove it with an independent validation gate before treating the observability surface as release-ready.

- Scan free text and dimension values for forbidden substrings, not just for known identifier fields, in every story that emits operator-facing text.
- Do not mark an epic `done` while its validation/verification stories remain in backlog; record an explicit, owned decision if they are intentionally deferred or waived.
- Reference the centralized `deferred-work.md` and `readiness-gates.md` from owning stories so carry-forward items have a named owner and trigger, especially since Epics 2–5 retrospectives are not yet written.
