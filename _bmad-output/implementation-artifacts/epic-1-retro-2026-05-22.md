Key strengths:

- Scope boundaries were documented directly in story records, especially around no transcript table, no EventStore internals in adopter contracts, no provider-session authority, and no Party personal-data persistence.

- Readiness gates were used as binding input rather than optional reference material.

## Challenges And Friction

Amelia (Developer): "The main friction was not coding a single feature. It was keeping multiple high-governance invariants consistent across contracts, aggregate behavior, server boundaries, projections, reads, diagnostics, and documentation."

Winston (System Architect): "Several design points had to be re-clarified mid-epic: identity taxonomy, tenant denial shape, projection freshness semantics, cursor safety, hydration degradation, and EventStore/publication boundaries."

Murat (Test Architect): "Some local evidence is intentionally not release evidence yet. That distinction is healthy, but it creates carry-forward work for Epic 5."

Recurring challenges:

- Contract wording and implementation had to be kept tightly synchronized. Story 1.2 created several deferred contract-evolution items that later stories had to work around.
- Idempotency required multiple hardening rounds, including pending-only completion, poisoned records, reservation identity, retryable uncertainty, audit-handle derivation, original rejection reason replay, and deterministic clocks.
- Read/query behavior created non-disclosure complexity beyond response bodies: cursor behavior, pagination metadata, counts, freshness states, headers, logs, and side channels.
- Hydration had to separate public degraded states from internal adapter failure reasons and avoid letting mutable upstream display data affect trust, sorting, filtering, cursors, cache keys, or freshness.
- Several performance and production-readiness items were consciously deferred because the repository still uses in-memory/local abstractions for foundation proof.

## Key Lessons

1. Foundation stories need explicit anti-scope as much as acceptance criteria.

   The strongest stories named what they must not implement. That prevented transcript-table authority, raw EventStore leakage, UI scope creep, provider-session identity, and upstream personal-data persistence.

2. Fail-closed behavior must be proven at the earliest boundary.

   Story 1.5 and later read/query stories show the pattern: authorization and syntax checks must happen before aggregate load, projection reads, cursor semantic evaluation, hydration, publication detail access, or protected delegate execution.

3. Local evidence and release evidence are different artifacts.

   Epic 1 produced strong local proof. Release-gate aggregation, signing, manifest traceability, provider portability proof, and formal schema evolution evidence remain later-epic responsibilities.

4. Public vocabulary consistency is a design asset.

   Reusing the same trust/freshness/error/schema vocabulary across contracts, server code, projections, tests, and documentation reduced drift and made review findings easier to close.

5. Non-disclosure is wider than JSON payloads.

   The team repeatedly found that safe behavior must include diagnostics, `ToString()`, logs, telemetry labels, cursor metadata, pagination shape, route behavior, headers, public test fixtures, and evidence summaries.

## Deferred Work And Technical Debt

The most important deferred items are not treated as blame. They are recorded decisions about scope and sequencing.

Process/status debt:

- `epic-1` remains `in-progress` in sprint status even though every Epic 1 story is `done`.
- Some story file lists omit pre-existing files touched by later story folders.

Contract and public-surface debt:

- Some identifier records intentionally do not support `with` cloning after validation hardening; adopter guidance should state this clearly.
- `ProviderCorrelationMetadata.ExtensionData` and related dictionaries still need bounded-size/key enforcement in a later contract-evolution pass.
- Some error/documentation URI and invalid-input behavior remains intentionally loose until the error-handling/onboarding stories own it.

Runtime and production-hardening debt:

- Idempotency executor wiring is complete for add-participant but still deferred for handlers that did not exist in Story 1.6 scope.
- EventStore command-status bridge exists as a primitive but is not wired into runtime terminal-outcome resolution.
- Projection accumulator deduplicates by `EventId`; same-EventId/different-payload poisoning is deferred to production read-model hardening.
- Query list handling enumerates an in-memory tenant set before paging; production stores need pushed-down filtering, sorting, and paging.
- Offset pagination is accepted for now but is unstable under concurrent mutation; production-grade keyset semantics remain deferred.
- Some tenant denial timing side-channel work is deferred to hardening/observability work.
- Hydration DTOs permit inconsistent `Resolved` and `HydrationState` combinations even though current service mapping is correct.

Release-evidence debt:

- Tenant isolation, idempotency, event schema evolution, provider portability, and conformance evidence need later manifest aggregation and signing.
- Full production upcaster/migration policy, production projection store mechanics, production rebuild scheduling, operational dashboards, and non-current trust-bearing exceptions remain outside Epic 1.

- Tenant-first access, typed fail-closed outcomes, idempotency behavior, projection freshness, and replay/rebuild proof are usable prerequisites for governance commands.
- Read-time hydration degradation is safely separated from durable state, which matters for governance views and audit evidence.
- Publication contracts and schema metadata provide a base for later governance event publication.
- Readiness gates for retention/deletion/tombstoning/legal hold/export/derived-index lifecycle and CORE status for sensitive/redaction commands are already decided.

Preparation needs that carried into Epic 2:

- Preserve tenant-first guard ordering for every governance mutation.
- Require audit pairing before successful governance state mutation.
- Keep redaction behavior distinct from durable event history and audit evidence.
- Ensure projection freshness blocks trust-bearing governance actions unless explicitly allowed by a later decision.
- Treat local Epic 1 evidence as input, not as substitute for release-gate evidence.

Significant discovery assessment:

- No Epic 1 finding invalidates the overall Epic 2 direction.
- Epic 2 must account for deferred idempotency wiring, audit/event evidence obligations, projection freshness blocking, and redaction replay safety.
- No PRD or Epic 2 rewrite is required from this retrospective alone.
