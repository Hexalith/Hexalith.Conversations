## 3. What Went Well

### Promotion pipeline became real

Epic 3 proved the pipeline across multiple capability types:

- Story 3.1 established the promote -> test -> adopt -> delete-or-facade -> conformance -> sibling proof -> submodule commit -> root gitlink pattern.
- Stories 3.2 through 3.6 repeated the pattern across tenant access, telemetry, ServiceDefaults, Aspire/Dapr hosting, publication, and serialization.
- Story 3.7 used the same discipline to build only the safe EventStore metadata subset and defer unsafe Conversations DTO adoption.

This was a meaningful step up from Epic 2. Epic 2 mostly consumed existing platform surface; Epic 3 changed shared modules while preserving dependent behavior.

### Behavior preservation held

Every story kept the public contract-shape diff empty. Conformance reached 361 and stayed stable from Story 3.3 onward. The strongest examples:

- Story 3.2 preserved fail-closed tenant access through a shared neutral evaluator plus Conversations-owned denial vocabulary.
- Story 3.3 preserved all seven metric counters, meter name, dimension keys, boolean tokens, lowercase enum tokens, and safe log event names.
- Story 3.4 preserved the existing ServiceDefaults runtime path through EventStore DomainService and avoided double registration.
- Story 3.6 preserved the 13 public event names and exact-before-suffix projection type lookup.
- Story 3.7 refused to reshape public DTOs for metadata adoption.

### Thin facades were the right compromise

The team repeatedly chose to delete duplicated mechanics while preserving stable domain entrypoints:

- `AddHexalithConversationsClient` stayed as a thin facade over the shared HTTP registration helper.
- Tenant access kept Conversations decision, requirement, denial, guard, and signal vocabulary over the shared evaluator.
- Telemetry emitters became wrappers over Commons diagnostics while retaining the Conversations metric contract.
- Serialization reduced ruleless converter skeletons to adapters over Commons while keeping prefixed identifier converters local.

That decision avoided unnecessary consumer churn and protected NFR6.

### Explicit deferral beat forced implementation

Story 3.7 is a positive example, not a failure. EventStore gained additive command/event metadata support, but Conversations public DTO adoption was deferred because it would have violated one or more stop conditions:

- public PascalCase command/event vocabularies must remain separate from EventStore kebab-case routing metadata,
- `CreateConversationCommand` must not grow a public aggregate identity,
- `Hexalith.Conversations.Contracts` must stay free of EventStore infrastructure coupling,
- public contract shape must remain unchanged.

The story recorded the deferral honestly instead of manufacturing a marker interface adoption that removed no real boilerplate.

### Reviews caught real release risks

The senior reviews repeatedly found uncommitted submodule changes, stale file lists, stale counts, or green-claim gaps before they became release evidence:

- Story 3.1 corrected a false Commons gitlink claim.
- Story 3.3 resolved an uncommitted Commons diagnostics promotion before final status.
- Story 3.4 fixed a red Commons ServiceDefaults test commit and a flaky meter-listener test.
- Story 3.6 committed review-hardening tests that had been left dirty in Commons and the umbrella.
- Story 3.7 committed uncommitted EventStore resolver test coverage and corrected the client test count.

This is strong evidence that adversarial review remained necessary and valuable.

## 4. Challenges and Growth Areas

### Finalization mechanics still rely too much on review

Epic 2's biggest process lesson was that story records and file lists drift if they are not generated from the final gate outputs. Epic 3 improved the discipline but did not eliminate the failure mode. Review still had to correct:

- stale test counts,
- incomplete File Lists,
- uncommitted submodule tests,
- root gitlink mismatch or ambiguity,
- outdated Completion Notes.

The core issue is unchanged: the workflow still permits a story to claim finality before the final source, submodule, and evidence state are mechanically verified.

### Submodule mechanics remained the primary operational hazard

Epic 3 intentionally touched Commons and EventStore. That was the point of the epic, but it exposed the same pattern repeatedly:

- submodule commits existed but root gitlinks lagged,
- root gitlinks were bumped in the working tree but not yet captured in the story commit,
- review-hardening tests were added after a submodule commit and initially left dirty,
- story text claimed a clean state that did not match `git status`.

The runbook helped, but the gate needs to be blocking and mechanical.

### VSTest execution was often unavailable in the sandbox

Several stories could not execute `dotnet test` through the usual VSTest path because local socket or named-pipe creation was blocked. The team documented this and used compiled xUnit v3 executables as the execution gate. That workaround was consistent and transparent, but the fallback should be made explicit in the test guidance so future records do not look like partial validation.

### Some shared surfaces now need real consumers

Story 3.7 added EventStore command/event metadata resolvers, but review noted they currently have tests and no production consumer. That is acceptable for a conditional FR-16 platform surface, but it should not quietly become permanent unused platform API.

### One Epic 2 technical thread is still not fully closed

The Epic 2 retro carried a high-priority read-store population concern. Epic 3 did not clearly close it. Story 3.5 promoted publication mechanics and modeled the AppHost, and Story 4.1 documents read-model/write-policy adoption, but the retrospective evidence does not prove that the projection write path is fully exercised by a production projection flow. This needs an explicit decision before final attestation.

## 6. Key Lessons

1. **Thin adapters are the safest way to extract shared mechanics from a pre-release domain module.** They removed boilerplate while preserving domain vocabulary and public entrypoints.

2. **A runbook is not a gate.** The promote/adopt runbook improved behavior, but story completion still needs a mechanical check for dirty submodules, root gitlink state, file-list drift, and final test counts.

3. **Conditional requirements need explicit stop conditions.** Story 3.7 succeeded because it named the exact public-contract hazards before implementation and stopped at the safe subset.

4. **Source-generated serialization and polymorphic lookup need contract-shape discipline.** Story 3.6 showed that shared helpers can remove ceremony without forcing contracts into platform-specific interfaces.

5. **Review-hardening tests must be committed as part of the same completion boundary.** Several stories had correct review additions that were initially left outside the committed submodule or umbrella state.
