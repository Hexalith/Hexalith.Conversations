## Challenges And Friction

Amelia (Developer): "The recurring friction was not a single feature; it was keeping content-safety guardrails precise enough to reject protected values without rejecting legitimate closed-vocabulary tokens. Stories 4.4, 4.5, and 4.6 each hit a version of the same trap where an over-broad blocklist collided with safe machine identifiers."

Winston (System Architect): "Several seams had to be re-clarified mid-epic: how compatibility status must not imply runtime authority, how a write-side API could be added without making the host runnable, how diagnostics must collapse access denials to a hidden shape, and where caller provenance is allowed to flow versus where it must never become authority."

Murat (Test Architect): "The most instructive review finding was Story 4.5, where the cross-tenant scenario was content-safety-proven against the fixture but never exercised through the machine-readable run result. A check marked done was materially incomplete until review drove it through the actual suite output. That is the difference between an assertion existing and the contract being proven on the real surface."

Paige (Tech Writer): "The open review point for documentation is drift surface. The guide deliberately consolidates and links, which is correct, but it means the canonical tables in the contract README are now load-bearing for two documents. The docs-validation net guards names and pointers; it does not guarantee the narrative stays readable as the surface grows."

Recurring challenges:

- Content-safety blocklist precision: the free-text leakage scan repeatedly collided with closed-vocabulary tokens (`subscription`, `party-`, `tenant-`, `error-envelope`, `case-`, `release-gate-tenant-isolation`). The resolved pattern is to run the `ConversationError.EnsureContentSafe` blocklist on free text only and enforce a bounded closed-token charset (excluding `:`/`\`/`/`) for machine identifiers.
- Compatibility metadata had to be kept as adopter-facing contract truth, not authorization, tenant, governance, freshness, or runtime-health truth; Story 4.1 review fixed invariant gaps where supported/unsupported status could carry contradictory remediation/error combinations.
- Transport realism: the Story 4.2 client initially treated non-seekable HTTP response streams as malformed, which would have mapped real successful responses to typed fallback errors; review caught and fixed this before close.
- Side-channel equivalence under diagnostics and conformance: denied, missing, cross-tenant, and unauthorized requests must collapse to the same hidden shape; Stories 4.4 and 4.5 both required review-added coverage to prove this on the real result path rather than only in unit fakes.
- A latent gap surfaced and was closed: `UpdateConversationMetadataCommand.Attributes` was carried as "safe adopter metadata" since Epic 1 but was not actually bounded by `ConversationCommandSchemaValidation` until Story 4.6 bounded it alongside the new caller metadata.
- One transient build-process friction was recorded in Story 4.3: a parallel `dotnet pack` of the client failed on a shared contracts DLL lock and succeeded on a serial rerun.

## Key Lessons

1. A single typed catalog beats parallel mappings.

   Story 4.3 collapsed compatibility errors, client fallback errors, and command-API error construction onto one `ConversationErrorCatalog`. Stories 4.4, 4.5, and 4.6 then reused it instead of inventing parallel error/remediation models. Centralizing the taxonomy removed the cross-surface drift that the story records repeatedly flagged as the main risk.

2. Content-safety scanning must target free text, not machine identifiers.

   The recurring blocklist collision across 4.4, 4.5, and 4.6 shows that protected-value disclosure scans belong on free-text fields, while closed-vocabulary tokens are safe identifiers and need a bounded charset rather than the disclosure blocklist. Over-scoping the scan blocks legitimate vocabulary; under-scoping it leaks. The line between the two is itself a design asset.

3. A check is not proven until it runs on the real output surface.

   The Story 4.5 review caught a check that passed against the fixture but never produced a result in the machine-readable run. Conformance, diagnostics, and side-channel guarantees must be exercised through the same artifact an adopter or CI would consume, not only through an adjacent unit assertion.

4. Provenance is not authority, and the boundary must be enforced by construction.

   Story 4.6 kept caller metadata as bounded, content-safe provenance that can never become tenant, authorization, governance, or trust truth. Correlation/causation stayed on the existing envelope; no new durable field was added because that would have triggered an ADR. Keeping the additive surface non-breaking preserved the public command envelope.

5. Documentation is a verifiable contract, and additive change avoids ADR churn.

   Story 4.7's docs-validation net makes "stale examples fail" real by resolving referenced type and error-code names against the shipped assembly. And across the epic, choosing additive optional parameters and reused contracts (rather than envelope or vocabulary changes) repeatedly kept stories clear of ADR triggers while still delivering the adopter surface.

## Team Agreements

- Keep one typed error catalog, one compatibility vocabulary, and one trust/freshness vocabulary across contracts, client, server, diagnostics, conformance, and docs; do not fork parallel models or surface-specific synonyms.

- Treat caller-supplied values as provenance only; they must never become tenant, authorization, governance, or trust truth, and additive contract changes are preferred over envelope or vocabulary changes that trigger ADRs.
- Treat "local evidence passed" as necessary but not sufficient for release evidence; hand the Story 4.5 conformance slice forward to Epic 5 intact.
- Keep `Program.cs` fail-closed and server endpoints opt-in; do not introduce a globally-runnable host, new durable state, or new public vocabulary without the relevant readiness gate or ADR.
