### B. Code at the story boundaries (verified lens findings)

#### F-4: Duplicate-event semantics diverge between domain replay and 16.2 projection replay

**Sources:**

- The domain side accepts a duplicate. `src/Hexalith.Conversations/Replay/ConversationReplayVerifier.cs:89-97`
  and its test `ConversationReplayVerifierTest.cs:64-76` accept the same `EventId` at a later stream position
  for `ParticipantAdded` and `ConversationProjectChanged`, as a no-op duplicate delivery.
- The 16.2 projection side rejects it. The binding includes the stream `Position`
  (`ConversationProjectionEventRecord.cs:47-54`). `Admit` marks any differing binding `MetadataContradictory`
  (`ConversationProjectionMaterializer.cs:928-942`), and `AllowsPersistence` then refuses the generation.
- Position-only `MessageId` values and caller-supplied contract `EventId` values share one `_bindings` map
  (`:693`, `:860`, `:900`).

Lenses: edge-case and adversarial, independently.

A history the domain accepts as valid therefore never projects again, and no repair path exists. Before 16.2
the materializer deduplicated on `EventId` only. Whether EventStore can persist such a history in production
is **unproven** (verdict PLAUSIBLE). The AD-8 frozen row ("same identity, different binding → contradictory")
and the domain verifier cannot both be right for these two event types.

A related unproven case is the adversarial lens's observation that contradictory input for an existing
conversation is rejected before any pending marker is written (`ConversationAsyncProjectionHandler.cs:180-189`
vs `:244`). The previous generation stays readable, and terminal reconcile re-dispatches into the same
rejection.

**Instance: decision and spec reconciliation (A-52).** **Prevention:** when a story redefines identity or
duplicate semantics, check the domain replay verifier as well as the projection.

The ownership split landed as designed:

- the pure transition and durable store in Tenants;

**internal** `ReadModelBatchCanonicalJson.Serialize` through
`<InternalsVisibleTo Include="Hexalith.Conversations.Server" />`

The persisted `ReplayStateHash` therefore depends on an unversioned internal API, and neither repository pins
it with a golden vector. `epic-16-context.md:48` requires "a versioned EventStore API and golden vectors first".

**Instance: defer to the EventStore owner (A-56).**
