Key strengths:

- Strong story-to-story continuity: each story reused prior contracts (trust posture, evidence entries, redaction attribution, command availability, verification contracts) and explicitly deferred later-story scope.
- Anti-scope was named in every story: no durable search/autocomplete/recent-search index, no transcript table, no second audit store, no evidence-bundle export, no Admin/FrontComposer shell scaffolded without an approved decision.
- Server-owned trust is consistent: trust, freshness, redaction, citation availability, audit readiness, verification state, and command eligibility all originate from projection/command metadata, never client inference.
- Review loops materially hardened each story, repeatedly catching fail-open defaults, disclosure-vocabulary gaps, and side-channel masking before the story closed.

## Challenges And Friction

Amelia (Developer): "The recurring difficulty was not building a feature; it was keeping the same disclosure invariant consistent across a growing set of read surfaces. Every new surface (search rows, evidence entries, redaction attribution, citation text, temporal links, command labels, verification summaries, demo evidence) is a new place where existence, redacted content, Party data, or substrate internals could leak, and each had to be proven closed independently."

Sally (UX Designer): "The biggest friction is structural: Epic 3 is UI-heavy by intent but has no UI. Every story consciously stopped at contracts/server/API and recorded UI/E2E as not applicable because no Admin or web project exists. That means the responsive, accessibility, clipboard, browser-title, telemetry, and screenshot promises are encoded as DTO fields and contract tests but have never been exercised against a rendered surface, an accessibility tree, an actual clipboard, or a real browser title. That is the entire reason 3.8A-3.8C exist, and they are still backlog."

Winston (System Architect): "Several safety decisions had to be re-clarified during review rather than at design time: trust-default direction for older/missing metadata, freshness aggregation across the full filtered set rather than the page window, canonical-placeholder enforcement, audit-readiness consistency between parent and child, strict composite-cursor parsing, mandatory command recheck, scoping verification evidence to the requested tenant/conversation, and what counts as genuine cross-tenant denial. The pattern is healthy but shows that the leak-by-default risk is real and easy to miss on a first pass."

Murat (Test Architect): "The test evidence is server-side proof, not operator-experienced proof. The story records themselves say so: redaction non-disclosure into hidden DOM, ARIA labels, tooltips, clipboard payloads, browser titles, responsive duplicates, and screenshots is asserted at the DTO/API level and explicitly deferred to 3.8A-3.8C. We have strong evidence that the data is safe and no evidence yet that the rendered, accessible, and copied surfaces are safe."

Recurring challenges:

- Leak-by-default was the dominant hazard. Reviews repeatedly found surfaces that defaulted to confident/visible/current instead of unavailable/hidden/unknown, including trust-preview fallbacks, malformed page-size fallback, and freshness aggregation that hid non-current matches.
- Disclosure-vocabulary evasion needed normalization. Story 3.5 review showed that literal forbidden-term checks could be bypassed by separator/casing variants (`Event Store`, `provider-payload`, `raw-exception`, `hidden field`), requiring normalized validation.
- Parent-state masking of child state recurred: a ready evidence entry could mask missing redaction audit readiness (3.3), and a parent citation/posture state could mask a missing or unsafe entry-level signal (3.3/3.4).
- Composite temporal cursors are subtle. Position-only parsing accepted mismatched projection segments (3.4), and the demo DTO initially rejected the canonical composite cursor the temporal contract requires (3.7).
- The no-UI condition means the operator-facing safety surface is entirely unverified; responsive, accessibility, and leakage/clipboard/browser/telemetry behavior is designed but not proven.

## Key Lessons

1. Read epics need anti-scope as strongly as feature epics.

   Every Epic 3 story named what it must not build: no durable search/autocomplete/recent-search index, no transcript table, no second audit store, no evidence-bundle export, no mutation route on the read API, and no Admin shell scaffolded just to satisfy one story. That discipline kept seven stories on one disclosure-safe read boundary.

2. Missing metadata must degrade, never default to safe.

   The most common review fix across 3.1-3.7 was forcing older/missing/ambiguous metadata to unavailable/unknown/blocked rather than confident/current/visible. Absence of a trust signal must never imply authorization, freshness, citation readiness, audit readiness, verification, or command eligibility.

3. Disclosure surfaces multiply with every read feature, and each needs its own proof.

   Search counts and facets, why-visible explanations, evidence entries, redaction placeholders, audit detail, citation copied text, temporal URLs, command labels, verification summaries, and demo evidence are all distinct disclosure surfaces. Safe behavior had to be re-proven for each, and reviews showed the gaps are easy to miss.

4. The server owns trust; the rendered surface is the unverified frontier.

   Trust posture, freshness, redaction, citation/audit availability, verification state, and command eligibility are all server-owned and well tested. But because there is no UI, the rendered DOM, accessibility tree, clipboard, browser title, telemetry, and responsive duplicates are designed-only. Server-side proof is necessary but not sufficient for an operator-facing investigation workspace.

5. Privileged and verification paths must reuse existing audit and freshness gates, not invent side channels.

   Story 3.5 kept command execution advisory and always server-rechecked; Story 3.6 required an existing `PrivilegedOperationalActionClass.Verify` justification before touching tenant data and never appends events or mutates state; Story 3.7's demo composes existing read services without creating a new write path or authority. Verification and demo are derived evidence, not new sources of truth.

## Deferred Work And Technical Debt

The most important deferred items are not treated as blame. They are recorded decisions about scope and sequencing. The single largest carry-forward item for Epic 3 is the entire 3.8 verification gap.

The 3.8 verification gap (highest priority):

- `3-8a-verify-responsive-layout-and-mobile-safe-triage` is `backlog`. Trust ordering (tenant scope, record identity, trust posture, evidence completeness, command eligibility before timeline reliance) at desktop/tablet/mobile/wide-desktop breakpoints, mobile safe read-only triage, permission-safe DTOs behind responsive cards/sticky headers/drawers/condensed summaries/skeletons/hidden regions/duplicated markup, and high-contrast/reduced-motion/zoom states are not verified. CSS/viewport/visually-hidden text must never act as authorization, and this has never been exercised against a layout.
- `3-8b-verify-accessibility-tree-keyboard-and-screen-reader-safety` is `backlog`. Focus order and announcements exposing trust posture, evidence completeness, and blocked-action reasons before sensitive content, absence of redacted/unauthorized content from accessible names/descriptions/live regions/headings/table summaries/focus announcements/clipboard output, keyboard-only Find -> Read -> Trust flows, and WCAG 2.1 AA expectations are not verified.
- `3-8c-verify-leakage-clipboard-browser-and-telemetry-disclosure-safety` is `backlog`. Leak Sentinel scanning for forbidden strings/structured values across rendered DOM text/attributes/ARIA properties, page title, clipboard output, telemetry envelopes, screenshots, and accessibility snapshots is not implemented. Browser titles, route metadata, tooltips, toasts, empty/loading/denied states, and telemetry events have only DTO/API-level safety checks, not rendered-surface proof.
- Cross-cutting consequence: each of 3.1-3.7 explicitly scoped responsive/accessibility/clipboard/browser-title/telemetry/Leak-Sentinel verification out and into 3.8A-3.8C. The canonical fixtures defined in Story 3.7 are intended for 3.8 reuse, but the 3.8 evidence checklist, fixture sets, owners, pass/fail gates, and conformance-manifest traceability remain unwritten.
- Process/status debt: `epic-3` remains `in-progress` and `epic-3-retrospective` was `optional` even though 3.1-3.7 are `done`; the epic is feature-complete but not verification-complete, and sprint status sends a mixed signal.

UI/host scaffolding debt:

- There is no `Hexalith.Conversations.Admin`, web UI, CLI, worker, or conformance project in the solution. Every Epic 3 story produced trust-component-ready DTOs and recorded UI/E2E as not applicable. The custom trust primitives the UX specification calls for (`Trust Fact`, `SafeReasonInline`, `Freshness Marker`, `Command Availability Marker`, `Citation Control`, `Participant Identity Marker`, `Redaction Placeholder`) are designed contracts only.
- Story 3.6 verification and Story 3.7 demo are service-only by deliberate choice; no HTTP execution surface, CLI, or host was scaffolded. A future self-serve buyer-acceptance host and a verification execution surface are unbuilt.

Contract and behavior debt carried inside Epic 3 scope:

- Provider-portability verification in Story 3.6 returns not-applicable/deferred with explicit release-scope classification where the full portability proof is not yet implemented, rather than a real pass.
- Verification state is intentionally not projected into search/trust models; `ConversationVerificationState.Unknown` remains the default until a durable server-owned verified result source exists. Surfacing verified state into search/list (with non-enumeration preserved) is future work.
- The evidence summary distinguishes module evidence from inherited platform controls but does not produce a signed conformance artifact; full signed evidence bundle export, release manifest signing, and named waiver lifecycle are explicitly out of scope and owned by later epics.

Carry-forward from earlier epics (still open per `deferred-work.md`):

- Production read-store push-down, keyset pagination, and tenant-denial timing side-channel hardening remain deferred from Epic 1; Story 3.1's filters were applied on the same in-memory `IConversationProjectionReadStore` and inherit these limitations.
- Idempotency runtime wiring for non-add-participant handlers and the EventStore command-status terminal-outcome bridge remain deferred; Epic 3 is read-only and did not re-engage them.
- Release-evidence aggregation, signing, and manifest traceability for tenant isolation, redaction replay, projection rebuild, and provider portability remain later-epic responsibilities; Epic 3's verification output and demo evidence are inputs to that work, not the signed artifact.

## Team Agreements

- Keep all Epic 3 read surfaces on the single tenant-first, projection-owned, fail-closed read boundary; do not fork parallel transcript, viewer, audit, citation, or verification stacks.
- Missing, stale, ambiguous, or older metadata degrades to unavailable/unknown/blocked. Absence never implies authorization, freshness, citation/audit readiness, verification, or command eligibility.
- The read API stays GET-only and mutation-free; privileged actions remain advisory metadata that always rechecks at the command-handler boundary, and verification/demo paths never become a write path or new authority.
- Treat the rendered surface (responsive, accessibility, clipboard, browser title, telemetry, screenshots) as unverified until 3.8A-3.8C produce evidence; server-side proof is necessary but not sufficient.
- Do not scaffold an Admin/FrontComposer shell, export system, or new authority to satisfy one story; record an explicit scope decision instead, and reuse one canonical fixture set across verification stories.
- Continue contract-first, closed-vocabulary, no-Party-personal-data, no-EventStore-internals discipline for every additive public contract, and document intentionally unsupported behaviors for adopters.
