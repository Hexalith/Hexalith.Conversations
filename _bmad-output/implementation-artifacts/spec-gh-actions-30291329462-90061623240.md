## Intent

**Problem:** Hexalith.Tenants release run `30291329462`, job `90061623240`, failed at semantic-release `verifyRelease`: `[publication-preflight] version-collision: A proposed NuGet package version already exists.` for `3.3.0`. `Hexalith.Tenants.Contracts`, `.Server` and `.Aspire` were published from that repository up to `3.15.1` in May 2026; tags `v3.2.0`–`v3.15.1` were later deleted, so semantic-release derives versions from a tag line (`v3.2.18`) inside an already-consumed range. Every version from `3.3.0` to `3.15.1` is taken, so any minor bump is a permanent hard stop. A second defect hides this: `@semantic-release/github`'s `fail` step returns HTTP 422 creating its issue, so the log ends with an octokit error instead of the collision.

**Approach:** Make the version floor an explicit repository invariant. The fix commit carries a `BREAKING CHANGE` footer so the next release is `4.0.0` — above every consumed version, and semver-honest against `3.15.1`, whose consumers have two real API breaks waiting for them; the preflight bridge declares a minimum release version so a version line that slips below it fails closed locally, with an actionable message, instead of on a late destination probe; and the GitHub plugin's success-path comment and label writes are disabled, as Hexalith.EventStore already does.

*Renegotiated 2026-07-28 after review (supersedes the approved wording above it in this paragraph): the annotated `v3.15.1` floor tag is **not** created. Review established that semantic-release reaches `4.0.0` from the existing `v3.2.18` tag plus the breaking footer, so the tag changed no outcome while making `v3.15.1` resolve to the `3.2.18` tree rather than to `5469a6b`, where those packages were really built. The fail path keeps the pre-existing `"labels": []` rather than disabling failure issues.*

## Design Notes

**Fail path (human-ratified).** Between approval and implementation, another session merged `25fcb4d`, which sets `"labels": []` deliberately — its spec states the goal as making "failure reporting independent of a pre-existing GitHub label". That is kept. The plugin's default `labels` is `["semantic-release"]` and `fail.js` appends `RELEASE_FAIL_LABEL` (the same string), so the failing run's payload carried the label twice; `labels: []` leaves exactly one. Failure issues therefore keep working and no `failCommentCondition` change is needed. This change adds only the success-path disables.

**Related concurrent work.** `25fcb4d` also added `recover-partial-release.yml` for the same run. Its acceptance criterion completes `3.3.0` by publishing only the two absent packages, but the three "existing" `3.3.0` packages were published 2026-05-02 from unrelated source — this run never published anything. Dispatching that recovery for `3.3.0` would ship `Client`/`Testing` `3.3.0` from current source alongside three May-2026 packages at the same version. The recovery workflow does not call this bridge, so the floor does not block it. Recorded in `deferred-work.md`.

**Where the floor sits in the sequence.** The bridge rejects a below-floor version before the shared preflight touches any destination, but `.releaserc.json` runs `validate-release-secrets.sh` first, so release secrets are presence-checked before the floor is evaluated. The floor precedes network probes, not every secret read.

That gate was added to Hexalith.Builds on 2026-07-19 (`0b838f2`), one day after the last successful Tenants release (`3.2.18`, 2026-07-18), so it has never passed for this repository. Out of this spec's scope.

**Residual state:** the GitHub Release object for `v4.0.0` was never created, since semantic-release failed before its GitHub publish step.
