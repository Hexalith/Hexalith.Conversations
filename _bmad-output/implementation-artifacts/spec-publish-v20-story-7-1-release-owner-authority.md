## Design Notes

The trust anchor lives in publisher/test source, not V20 or V21. The verifier writes a temporary `principal public-key` allowlist, supplies it with command-scoped Git configuration, and compares `%G?`, `%GS`, and `%GF` to exact constants. This makes local Git trust configuration irrelevant and makes a future key rotation an additive authority change.

V21's tooling parent is the only commit allowed to change the spec, publisher, tests, workflow, and new schema. V21 itself adds only its JSON record. It binds the exact historical chain and V20 bytes/signature facts; it does not repeat the owner rationale as a new decision. Effective hold is `ACTIVE` when V21 is absent, `FAIL/BLOCKED` when present evidence is invalid, and `LIFTED` only after committed V21 validates.

Inventory distinguishes evidence time from implementation time. It validates frozen observations and checkpoint bindings at the commits that created them, keeps authority/non-implementation inputs immutable at evaluated descendants, and leaves declared Story 7.1 implementation paths for the final-record generator to bind at `SC-7.1`.

V21 lifecycle validation distinguishes historical state from endpoint state. Absence is `not-applicable` only with complete history and no reachable addition; shallow or unavailable history is `BLOCKED`, and deletion after publication is a visible failure. Descendant validation walks every commit newly reachable from the candidate relative to V21, including side branches forked before V21. A single-parent commit is compared with its parent. A merge already containing V21 is compared with the V21 publication tree; a pre-V21 side-branch merge is compared with its first parent while all introduced parent lines are inspected independently. This accepts allowed-only pre-V21 merges and unchanged V21 brought through any parent while still rejecting protected merge-result drift. Exactly the declared implementation paths plus five canonical JUnit results and two final-record outputs remain allowed.

Authority publication discovery uses full-history traversal and rejects more than one addition even when Git's default path simplification would show one. Lifecycle checks apply the same history-aware addition/removal rule to inventory, V19, V20, and V21, while preserving the known valid V19/entry/V20 pre-V21 states.

The SSH command scope overrides the allowed-signers file, `gpg.ssh.program`, `gpg.ssh.revocationFile`, and `gpg.minTrustLevel` before verifying V20. Check-mode inventory never resolves its unused worktree target. Descriptor reads and publication first resolve the physical root and record its identity, then open every absolute component from `/` with directory/no-follow flags and require the final descriptor identity to match. All relative traversal stays beneath that pinned descriptor. Content validation and temporary durability finish before the no-clobber link; that link is the commit point. Later failures are visible blockers but never trigger target unlink, and cleanup clears ownership as it closes/unlinks so retries cannot double-release resources.

GitHub's protected job identity is `job.workflow_repository`, `job.workflow_ref`, and `job.workflow_sha`; the source workflow requires the exact repository plus `...planning-authority-preflight.yml@refs/heads/main` and a full commit available in the checkout's complete object store. The first post-checkout program is inline protected-source shell: it discovers the candidate's lifecycle/tooling commit without executing repository code, compares each of the five tooling paths and modes with the source commit, then extracts and runs `_bmad/scripts/publish_story_7_1_successor_authorities.py` from `job.workflow_sha`, never from the candidate. Recognized immutable V19/entry/V20 stages use that source verifier and remain valid `ACTIVE` states without requiring the later workflow mirror; tooling/V21/descendants require exact source/candidate tooling bytes before package, configuration, or test execution.

CI wiring validation covers the exact `contents: read` permission, sole `planning-authority` job, complete approved step inventory, source identity variables, and source-verifier extraction. The integrated CI-trust route consumes effective repository rulesets including inherited organization rulesets and requires an active required-workflow rule selecting the exact source repository/ref/path, an observable empty bypass set, and direct-push protection. Missing API access, omitted bypass data, no matching rule, or any unverifiable field is `V21_CI_RULESET_ACTIVATION_UNVERIFIED/BLOCKED` and exits nonzero. That external result does not change local V21's machine-derived `LIFTED`; it determines whether CI may claim enforceable authority. Current live state remains blocked, and no candidate-controlled evidence can unblock it.
