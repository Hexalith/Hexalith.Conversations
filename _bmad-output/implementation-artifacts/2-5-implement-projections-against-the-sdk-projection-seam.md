## Story

As a Conversations maintainer,
I want the conversation projection implemented against the EventStore SDK full-replay projection seam (`IDomainProjectionHandler`) — so the generic replay-loop / dispatch / discovery-registration orchestration is delegated to the SDK while the conversation-specific field selection, freshness formula, and evidence construction stay in the module,
so that the hand-rolled projection orchestration frame disappears, the projection is served behind the shared `/project` endpoint the gateway actor invokes, and projection rebuild / freshness / degraded-state behavior is provably unchanged.

This is the **fifth story of Epic 2** (Consume Existing Technical-Module Surface) and the fifth `src/` production change in the initiative. It covers **FR-6**. Relevant NFRs: **NFR1** (behavior preservation), **NFR2** (no hot-path regression — snapshot/projection use preserved), **NFR5** (replay safety — full-replay projection is idempotent and tolerant of duplicate/out-of-order delivery), **NFR8** (public-surface / EventStore-concept boundary preserved — the SDK seam is server-side; the adopter API stays the unchanged Conversations DTOs).

> **READ THIS FIRST — disposition correction (Promote → Consume), mirroring the 2.4 precedent.** The Consume/Promote/Keep inventory labels the `projection-orchestration` area (`src/Hexalith.Conversations.Server/Projections/**`, **1,800 LOC**) **Promote** → FR-6. But the target capability — `IDomainProjectionHandler` + `DomainProjectionDispatcher` + convention discovery (`AddDomainProjectionHandlers`) behind the shared `/project` endpoint — **already exists** in `Hexalith.EventStore.DomainService` (verified at gitlink `ad2c957`). There is **nothing to promote into EventStore**: the seam ships today (the `Counter` sample and `WidgetDomain` test fixture both implement it). The honest disposition is therefore **Consume** — *adopt the existing SDK seam and delete the local orchestration frame* — exactly the "epics-label-vs-reality" correction Story 2.4 made (its labelled "remove-and-replace" was really "greenfield-adopt"). Record this Promote→Consume disposition correction per the Story 1.5 escape hatch in the FR-20 ledger (`Story25StructuralDispositions`), consistent with `Story22`/`Story23`/`Story24StructuralDispositions`. Whether this also warrants an inventory `changeLog` reclassification entry vs a story-scope disposition note is **AC-5 / Task 6** — follow the 2.4 reasoning (the area's *outcome* — local orchestration deleted — is identical under either label; the SDK seam pre-existing is the only material fact that moved).

Its `Project(...)` body is two parts: **(a)** a thin orchestration frame (instantiate `ProjectionBuilder`, `foreach event → builder.Apply(record)`, assemble the summary/detail records) — this is the *generic replay loop* the SDK seam delegates; **(b)** the conversation-specific logic — `ProjectionBuilder` (the event accumulator with idempotent `Apply(...)` per event type), `CreateFreshness`, `CreateSearchTrustPreview`, `CreateTrustPosture`, `DefaultCommandEligibility`, `CreateEvidenceEntries` — this is **Keep** (field selection, freshness formula, evidence construction). Story 2.5 moves (a) behind the SDK seam and **preserves (b) byte-for-byte in behavior**. The `Contracts/Projections/**` DTOs (`ConversationSummaryProjectionV1`, `ConversationDetailProjectionV1`, `ProjectionFreshnessV1`, `ProjectionFreshnessReasonCode`, …) are a **separate Keep area** (`projection-field-selection-freshness-shape`, 1,175 LOC, in the 196-type public baseline) — **do not reshape them**.

## Dev Notes

### The gateway-blob vs query-store duality — the central design decision (resolve & record)

The SDK seam's own XML docs are explicit (verified): *"This is the domain side of the platform's **stateless full-replay** projection model: the handler receives the aggregate's complete event sequence … and rebuilds the read model from scratch, returning the current state as a `ProjectionResponse`. It holds no state between calls and does not read or persist prior projection state — the gateway's projection actor stores and serves the single returned read model. Persisted, incrementally-merged multi-read-model state is a separate platform capability (the … read-model store consumed by query handlers), not this seam."*

That maps onto two **distinct** Conversations persistence paths:
- **Gateway path (this seam, 2.5):** `IDomainProjectionHandler.Project(...)` → one `ProjectionResponse(ProjectionType, JsonElement State)` blob → the EventStore gateway projection actor stores/serves it (invoked via Dapr behind `/project`).
- **Query path (Story 2.4 substrate):** the 5 query/governance services read `IConversationProjectionReadStore` → `IReadModelStore` (per-conversation key + per-tenant index), written by `ConversationProjectionReadModelWriter` via `ReadModelWritePolicy`. **Story 2.4 built this writer but explicitly did not wire it to be invoked on replay** (2.4 Open-Question-3 / LOW-2: *"Story 2.5 (FR-6) owns the replay-ordering that drives the writer"*).

**The decision:** does 2.5's handler *also* drive `ConversationProjectionReadModelWriter.PersistAsync(...)` to feed the query side (closing the population gap), or stay a pure seam adapter returning the blob?
- Arguments to wire it: 2.4 earmarked exactly this for 2.5; otherwise the production query-side read store is never populated and the 5 services read empty state (a pre-existing gap, not a 2.5 regression, but 2.5 is its natural owner).
- Friction: `IDomainProjectionHandler.Project(...)` is **synchronous**; `PersistAsync` is async (sync-over-async is an anti-pattern). And the seam is *meant* to be stateless — driving a stateful write from inside it cuts against the platform model.
- **Recommended default:** keep the **epics AC** the contract for what 2.5 *must* deliver (delegate orchestration via the seam; keep field/freshness/evidence; rebuild/freshness conformance green; retire plumbing tests; gate holds). Treat read-store population as the **scoped follow-on decision**: if it fits cleanly (e.g. the gateway already persists, or a separate async projection-write path can call the writer outside the sync seam), wire it and record it; if it would force sync-over-async or balloon scope, implement the pure seam adapter and **explicitly record the still-open production read-store-population thread** so it is not silently dropped. **Do not** invent a sync-over-async write inside `Project(...)`. Record the final call + rationale in the Dev Agent Record.

### Freshness-input sourcing (the seam is stateless)

The kept `Project(...)` takes `projectionGeneratedAt`, `staleAfter`, `isRebuilding`, `metadataWriteFailed` — none are on `ProjectionRequest`. Source them explicitly:
- `projectionGeneratedAt` → injected `TimeProvider.GetUtcNow()` (deterministic-replay rule — never bare `DateTimeOffset.UtcNow`). The handler is a singleton; inject `TimeProvider` via ctor.
- `staleAfter` → the **existing** configured threshold already used on the read/materialize path. Reuse the same value/source; do not introduce a new config key.
- `isRebuilding` / `metadataWriteFailed` → a stateless full-replay seam has no prior-state knowledge, so these can't be inferred from the request alone. Determine how the current system supplies them (the rebuild verifier sets `isRebuilding`; `metadataWriteFailed` reflects a write-side signal) and decide the honest value when serving through the seam (most likely `false` for the steady-state full-replay path, with rebuild/metadata-failure freshness still exercised through `ConversationProjectionRebuildVerifier` / the read-service degraded-state path). **Record the reconciliation** — this is the subtle correctness point reviewers will probe.
