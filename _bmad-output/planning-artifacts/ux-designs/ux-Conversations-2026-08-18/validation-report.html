Conversations UX Preservation Set — UX Design Validation Report

_bmad-output/planning-artifacts/ux-design-specification.md · ux-requirement-map.md · ux-design-directions.html

The legacy preservation set is an unusually rigorous behavioral and safety contract — states, fail-closed rules, leakage discipline, and acceptance identifiers extract cleanly, and the 52-decision/28-AC inventory is enforced by a named validator (epics.md:2599, Story 8.2). It is, however, not a visual contract: not one color value or Fluent token binding is committed anywhere in the markdown — the only concrete palette lives unbound in ux-design-directions.html — and 8 of the 11 frontmatter inputDocuments no longer exist on disk. A downstream consumer can build the behavior faithfully today; any consumer asked to mirror the visual design must invent values, which for a trust-critical UI (redaction vs. warning vs. degraded) is exactly where invention is unsafe.

The extra lenses sharpen rather than overturn that picture. Authority alignment is clean: the requirement map is a managed companion the V9 publisher rebinds at every candidate rebind, and at HEAD it pins exactly what the newest V14 sidecar pins — no critical or high findings — though its currency is time-limited by approved-but-uncommitted amendments that guarantee an imminent candidate rebind. Downstream consumability confirms identity-level extraction is exact (28/28 ordered AC parity) but finds that four required fields of the Story 8.1 disposition row schema have no source anywhere in the set, and that the freshness vocabulary splits three ways between spec and architecture despite the one-shared-enum mandate. Accessibility finds an unusually deep floor for a planning artifact, held back by two structural gaps: the floor is pinned to WCAG 2.1 AA rather than 2.2 AA, and blocked governance actions have a committed outcome but no committed mechanism for exposing their reason to keyboard and screen-reader users.

Accessibility review

review-accessibility.md

For a planning artifact, this spec commits an unusually deep accessibility floor: accessibility is framed as part of the trust model rather than polish, every load-bearing trust state has a committed non-color treatment with a named component and fail-closed states, and the redacted-vs-missing-data distinction — the hardest screen-reader problem on this surface — is explicitly solved with a microcopy taxonomy and a dedicated fixture. Two structural gaps keep it below a current-standard commitment: the floor is pinned to WCAG 2.1 AA (not 2.2 AA) in all three normative places, and the mechanism by which a disabled governance action exposes its blocked reason to keyboard and screen-reader users is never specified, even though disabled buttons are unfocusable and silent by default. The direction mocks pass AA text contrast on all five status treatments, but with almost no headroom and with the token values never bound into the spec. Check verdicts: stated floor adequate · state perceivability strong · announcements adequate · keyboard & focus adequate · Fluent inheritance adequate · direction mocks adequate · regulated-language surfaces thin.

high

Accessibility floor pinned to WCAG 2.1 AA, not 2.2 AA

spec:744, 1424, 1499; map:72 (UX-DR44)
2.2-only AA criteria are formally untested: Focus Not Obscured (2.4.11) is directly load-bearing given sticky trust bands, persistent headers, and drawers over a focused timeline; Target Size Minimum (2.5.8) applies to all pointer input while the 44px commitment is conditioned on touch support; Redundant Entry (3.3.7) touches the rationale-driven governance forms. Automated checks scoped to "WCAG 2.1 AA issues" would pass a UI failing current AA.
Fix: Rebaseline all three statements and UX-DR44 to WCAG 2.2 AA; add an explicit Focus Not Obscured obligation for sticky trust bands/drawers and an unconditional 24×24 minimum target size.
high

Blocked-action exposure: committed outcome, no committed mechanism

spec:747, 1050, 1112; html:732
Disabled buttons are unfocusable and silent to keyboard/screen-reader navigation by default, so "reason text without requiring hover" is unreachable for exactly the users the spec protects; the mocks reinforce the trap by carrying the reason as the disabled button's own label in a WCAG-contrast-exempt treatment. A keyboard or screen-reader operator cannot discover why a governance action is blocked — and may wrongly infer the action does not exist.
Fix: Commit the pattern: blocked Command Gates stay focusable (aria-disabled="true", not disabled), the safe reason is associated via aria-describedby, and adjacent visible reason text meets 4.5:1 independently of disabled styling; add this to the Command Gate row and the accessibility test list.
medium

Live-update announcement is intent-level

spec:1434; AC-RESP-006
One "should" sentence covers all trust, freshness, command-availability, and permission changes — no politeness levels, no rebuild-complete or stale→current announcements, no focus/announcement policy when redaction replaces content mid-read, no toast-vs-live-region channel decision. A screen-reader operator can keep relying on a view that silently went stale — the exact "no silent confidence" failure the spec forbids.
Fix: Specify per state-change class: politeness (freshness = polite; command-availability loss and redaction-in-place = assertive), required announcement copy pattern (state word + next safe action), and add stale-transition and redaction-replacement announcements to the acceptance criteria.
medium

Contrast targets declared but never bound to values

spec:729–734, 744; html chip values
Domain semantic tokens are named without colors; the only concrete values live in the non-normative mocks, where the two most safety-relevant treatments pass with almost no margin (verified 4.74:1, warning/stale 4.78:1 at 11px). Implementation-time token drift (theming, dark mode, Fluent alias remap) would silently drop freshness and trust treatments below AA with no spec-level check.
Fix: Bind minimum ratios (and the mock hex values as reference implementations) to each --conversation-status-* token, require ≥4.5:1 at rendered chip size in both themes, and add a token-level automated contrast test to the quality gates.
medium

No localization commitment for regulated microcopy

spec:833, 1030, 1449–1456
The denial/redaction/audit state words and safe-reason explanations exist only as English strings; the taxonomy's semantic contrasts (Redacted ≠ Unavailable ≠ Restricted) carry governance meaning that must survive translation. A translated deployment could collapse the redacted/unavailable distinction and mislead operators about whether content exists.
Fix: Require reason codes + localizable message-catalog keys for all safe-state words, with a translation acceptance check that the five state words remain pairwise distinct in every supported locale.
medium

Fluent inheritance is category-level; rc.2 risk unacknowledged

spec:978–989, 1315–1321
No component or variant is named (no FluentDataGrid/FluentDialog-level mapping), so "focus behavior, disabled states, keyboard behavior, and accessibility foundations from Fluent UI" is an unvalidated assumption for dialogs, drawers, grids, and tabs at 5.0.0-rc.2 quality. Teams may treat inherited surfaces as accessibility-done and skip verification exactly where the spec provides no custom obligations.
