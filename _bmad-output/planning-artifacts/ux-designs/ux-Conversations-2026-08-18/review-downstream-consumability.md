# Downstream Consumability Review — Conversations Legacy UX Set

## Overall verdict

**Broken as a direct architecture, story-development, implementation, or test contract; adequate as a preservation inventory and non-activation gate.** A consumer can mechanically recover the closed `UX-DR1`–`UX-DR52` and 28 acceptance-ID inventories and can unambiguously determine that no product-UI work is currently authorized. A consumer cannot, however, turn the preserved material into exact components, DTO bindings, state machines, stories, or executable acceptance tests without making safety-relevant choices that the UI is expressly forbidden to infer.

The correct present downstream action is therefore **preserve and do not implement**. Before any separately approved activation, the set needs an additive, machine-readable activation/disposition layer that binds every visual state and component to exact contract types/fields, source anchors, requirement IDs, release scope, and executable test obligations; the currently unbound legacy source should not be silently rewritten.

## Adversarial findings

### 1. Source-owned trust states do not have one canonical UI vocabulary

- **Severity: critical**
- **Impact:** The UX repeatedly forbids client-side trust inference, yet its component tables introduce visual states that cannot be mapped mechanically to the public contract. `Freshness Marker` expects `current`, `possibly-stale`, `stale`, `unknown`, and `conflicting`; result/header/command components additionally use `denied`, `restricted`, `degraded`, `incomplete`, `blocked`, `metadata-unavailable`, and other labels (`_bmad-output/planning-artifacts/ux-design-specification.md:1033,1042,1043,1045,1050,1096`). The source-owned `ProjectionTrustState` exposes only `Current`, `Stale`, `Rebuilding`, `Unavailable`, `Forbidden`, and `Redacted` (`src/Hexalith.Conversations.Contracts/TrustStates/ProjectionTrustState.cs:21,26,31,36,41,46`), while several of the UX concepts appear instead as separate freshness reason codes (`src/Hexalith.Conversations.Contracts/Projections/ProjectionFreshnessReasonCode.cs:21,26,31,36,41,51`). The preserved PRD also names `current`, `stale`, `rebuilding`, `unavailable`, and intentionally hidden as the freshness semantics (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/prd.md:505,662`). An implementer must therefore invent a many-to-many mapping or synthesize states client-side, directly contradicting the source-owned/no-inference invariant (`_bmad-output/planning-artifacts/ux-design-specification.md:317,319`). That ambiguity can produce false confidence, unsafe action enablement, or disclosure-distinguishing copy.
- **Fix:** Under separate release authority, publish a closed mapping with columns for `contract type`, `field`, `wire value`, optional `reasonCode`, `UX display state`, `precedence`, `copy key`, `allowed actions`, and `fail-closed fallback`. Treat every non-contract term as either a pure presentation label with an explicit mapping or a proposed server-contract addition. Require generated conformance tests to reject unmapped and duplicate mappings.

### 2. Component inputs are concepts, not exact schema bindings

- **Severity: high**
- **Impact:** The document offers “recommended contract concepts” named `TrustPosture`, `EvidenceItem`, and `CommandAvailability` (`_bmad-output/planning-artifacts/ux-design-specification.md:243,247`) and later permits an `EvidenceTrustModel` “or equivalent” (`_bmad-output/planning-artifacts/ux-design-specification.md:999,1137`). The primitive matrix says every primitive should have a defined source field, but its `Source Field` cells remain generic phrases such as “projection freshness metadata” and “authorized citation metadata” (`_bmad-output/planning-artifacts/ux-design-specification.md:1208,1212`). In contrast, the repository already has exact source-owned contracts: `ConversationEvidenceTrustPostureV1` defines the trust fields and their types (`src/Hexalith.Conversations.Contracts/Queries/ConversationEvidenceTrustPostureV1.cs:16`), `ConversationCommandAvailabilityV1` defines command availability and recheck fields (`src/Hexalith.Conversations.Contracts/Queries/ConversationCommandAvailabilityV1.cs:13`), and `ProjectionFreshnessV1` defines the freshness schema (`src/Hexalith.Conversations.Contracts/Projections/ProjectionFreshnessV1.cs:23`). Architecture cannot determine whether the UX names alias, replace, aggregate, or extend those contracts; implementation and tests cannot derive nullability, cardinality, serialization values, or authorization boundaries.
- **Fix:** Add a component-contract manifest that names the exact current DTO and property for every required input, plus transform ownership, null/absent semantics, cardinality, authorization precondition, and output copy key. Proposed fields must be separately marked as contract changes, never hidden behind “or equivalent.”

### 3. The journeys do not close over the canonical actors or requirement IDs

- **Severity: high**
- **Impact:** The canonical product baseline defines eight actors/journeys: Maya, Atlas, Sarah, Diego, Marcus, Julian, Helen, and Daniel (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/prd.md:421,425,426,427,428,429,430,431,433`). The UX contains four flow sections covering Sarah, Maya and Atlas, Diego, and Julian and Helen (`_bmad-output/planning-artifacts/ux-design-specification.md:849,880,906,931`); there is no Marcus audit-sink-degradation flow and no Daniel post-harm reconstruction flow. The UX source also contains no `Feature-FR*`, `Feature-NFR*`, or canonical journey IDs, even though the PRD establishes the behavior and quality obligations, including the 90-second diagnostic journey (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/prd.md:703`). A story author cannot mechanically prove that every canonical need lands on a surface/state, nor distinguish intentional non-UI coverage from an omitted flow.
- **Fix:** Publish a trace matrix keyed by canonical actor/journey and requirement ID, mapping each to UX flow, surface, component/state, acceptance IDs, and disposition (`covered`, `non-UI`, `deferred`, or `requires release decision`). Add explicit Marcus and Daniel paths or explicit, approved non-UI dispositions.

### 4. The 52 decision IDs are complete but their source anchors are not mechanically resolvable

- **Severity: high**
- **Impact:** `ux-requirement-map.md` has a useful closed inventory, but `Source Section` contains informal labels such as “Core experience / component strategy,” “Trust as a contract,” “Evidence cues,” and “Gated action tests” rather than a path plus stable heading/anchor or line span (`_bmad-output/planning-artifacts/ux-requirement-map.md:27,30,31,35,42`). Several labels summarize multiple locations, and none carries requirement, component, flow, or acceptance-ID dependencies. This is weaker than the already-planned Story 8.1 row contract, which requires `id`, `status`, `owner`, `rationale`, `sourcePath`, `sourceSha256`, `evidenceOrControl`, `historicalMappings`, `compatibility`, and `disclosureSafety` (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/epics.md:2563,2567`). A human can semantically search the monolith; an AI or generator cannot prove it extracted the intended load-bearing sentence rather than a nearby restatement.
- **Fix:** Generate the planned disposition bundle and add exact source anchors (path + heading slug and/or content digest), plus typed links to requirement IDs, component IDs, flow IDs, and acceptance IDs. Validate anchor resolution and digest parity. Do not substitute section-title normalization for an actual source binding.

### 5. Acceptance IDs are inventory-grade, not executable acceptance contracts

- **Severity: high**
- **Impact:** The map preserves all 28 identifiers, but each row carries only a broad source section, disposition, and historical provenance (`_bmad-output/planning-artifacts/ux-requirement-map.md:82,89`). The source statements are often compound—such as rechecking tenant, role, trust state, and metadata for every command, or requiring deterministic trust precedence—without a Given/When fixture, precise source values, expected UI output, test lane, or evidence artifact (`_bmad-output/planning-artifacts/ux-design-specification.md:1325,1328,1330`). Canonical responsive fixtures are listed separately (`_bmad-output/planning-artifacts/ux-design-specification.md:1533,1537`) but are not mapped to acceptance IDs. Test authors can invent plausible checks, but cannot demonstrate complete or non-overlapping coverage mechanically.
- **Fix:** For each UX AC, publish machine-readable `given`, `when`, `then`, viewport/input modality, exact fixture IDs, contract-state inputs, forbidden observations, required test lane, and evidence path. Include an AC-to-fixture/test many-to-many matrix and require every AC to have at least one positive and relevant fail-closed/negative assertion.

### 6. The UI-system contract is not version- or rule-complete

- **Severity: medium**
- **Impact:** The UX repeatedly says FrontComposer plus “Fluent UI Blazor” and assigns broad component ownership (`_bmad-output/planning-artifacts/ux-design-specification.md:269,300,978`), but it never pins Fluent UI V5 or carries the current Hexalith constraints that forbid legacy v4/FAST tokens and require `FluentAccordion` for page-like surfaces with multiple titled sibling sections (`references/Hexalith.AI.Tools/hexalith-ux-instructions.md:7,24,31,43`). A consumer following only the UX set could choose obsolete tokens, recreate theme styling, or design a nonconforming multi-section detail surface.
- **Fix:** In the activation layer, bind the inherited UI system as `FrontComposer + Blazor Fluent UI V5`, reference the governing repository instruction/version, list exact standard components for each composite, and record only the behavioral/visual deltas. Include explicit accordion placement for each multi-section page/dialog/detail surface and token conformance tests.

### 7. The UX uses “v1” as a design scope before the release slice is decided

- **Severity: medium**
- **Impact:** The chosen direction is called the “v1 design base” and includes command gates and governance detail (`_bmad-output/planning-artifacts/ux-design-specification.md:814,818,822`); later patterns include mutation-capable primary actions and governance-changing confirmation dialogs (`_bmad-output/planning-artifacts/ux-design-specification.md:1237,1239,1273`). The PRD says the v1 floor and v1.1 candidates are open/status-unverified (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/prd.md:441,442`) and explicitly leaves read-only Find/Read versus evidence export unresolved (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/prd.md:730`). Although the preservation banner prevents present execution, a future story splitter still cannot tell which actions are release scope and which are illustrative/future.
- **Fix:** Require the activation authority to publish a release-capability matrix for every action and surface (`in`, `read-only`, `blocked`, `deferred`, `out`) before stories are generated. Remove “v1” from downstream identifiers unless it points to that approved matrix.

### 8. Historical source provenance is not resolvable from the UX frontmatter

- **Severity: medium**
- **Impact:** Eight frontmatter inputs—the two product briefs and six research files—point to paths that are absent from the repository (`_bmad-output/planning-artifacts/ux-design-specification.md:23,30`). The memlog claims the specification is byte-frozen by a live-recomputed `7bbd057f…` binding (`_bmad-output/planning-artifacts/ux-designs/ux-Conversations-2026-08-18/.memlog.md:9`), but that purported protection is stale: the referenced V2 manifest is a `2.0.0-draft` with `pending-prerequisites` status, is bound to V6 authorities, and records obsolete hashes for both UX files (`docs/release-evidence/preservation-traceability-manifest-v2.json:5,6,13,14,15,50,51,55,56`). A source extractor therefore encounters both dead provenance paths and a materially incorrect workspace explanation of their current binding; it cannot distinguish authoritative inheritance, supersession, or orphaned input without external archaeology.
- **Fix:** Through governed additive authority, publish tombstones with original path, last authoritative revision/blob hash, deletion commit, disposition, and current replacement; bind the current specification and map hashes in the planned Story 8.1 disposition bundle; and append a corrective memlog entry through `memlog.py`. Do not silently rewrite the preserved source to conceal the provenance or binding gap.

## Evidence and mechanical notes

- The strongest mechanically consumable decision is the boundary: the UX specification says `preserved-not-activated` and requires separate approved release authority (`_bmad-output/planning-artifacts/ux-design-specification.md:32,33,34,44`); the map repeats it (`_bmad-output/planning-artifacts/ux-requirement-map.md:2,4,9,14`); architecture says v9 adds no UI implementation scope (`_bmad-output/planning-artifacts/architecture.md:1934,1938`); and the canonical spec package keeps the global hold active (`_bmad-output/specs/spec-Conversations/SPEC.md:31,33`). No downstream consumer should interpret this review as authority to implement.
- Mechanical extraction confirmed **52 unique decision IDs in numeric order** and **28 unique acceptance IDs in source order**, with the map's acceptance list exactly matching the identifiers in the UX specification. This makes denominator preservation strong even though semantic/source linkage is weak.
- The direction artifact now identifies **02. Split Investigation Lens** as chosen and declares its colors, borders, and degraded-state warning treatment non-normative (`_bmad-output/planning-artifacts/ux-design-directions.html:678,679`). It is safe as an illustrative reference only; it is not a component/schema contract.
- The intended remediation shape already exists in planning: Story 8.1 defines a closed disposition schema and exact row fields, while Story 8.2 defines zero-gap identity and drift validation (`_bmad-output/planning-artifacts/prds/prd-Conversations-2026-06-02/epics.md:2550,2563,2599,2605`). The declared `ux-preservation-disposition-v1` schema/JSON/Markdown and Story 8.1/8.2 final records were not present at review time, so downstream consumers currently have the legacy source/map pair rather than the planned executable handoff.
- Severity totals: **critical 1 · high 4 · medium 3 · low 0**.
