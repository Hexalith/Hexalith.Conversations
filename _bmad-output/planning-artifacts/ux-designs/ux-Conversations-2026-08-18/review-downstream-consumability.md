# Downstream Consumability Review — Conversations UX preservation set

Reviewed set: `ux-design-specification.md` (1,566 lines), `ux-requirement-map.md`, `ux-design-directions.html`.
Consumer side consulted: `architecture.md`, `prds/prd-Conversations-2026-06-02/epics.md` (Epic 8, Stories 8.1-8.2), `v9/story-contracts/8.1.json`, `_bmad-output/project-context.md`.
Reviewer lens: downstream consumability. No validated file was changed.

## Overall verdict

The set is mechanically consumable for its named owner: the map's 52 UX-DR rows and 28 acceptance IDs match Story 8.1's frozen inventories exactly, in order, and the spec is unusually well aligned with the FrontComposer generated-first mandate. However, the map's addressing into the spec is lossy (roughly half the "Source Section" labels are not headings, several are ambiguous, and the spec has two same-named H2 sections), four of the disposition schema's required per-row fields have no declared source anywhere in the set, and the freshness vocabulary diverges between the spec and architecture despite architecture's one-shared-enum mandate. A consumer can complete the Stories 8.1-8.2 parity extraction without guessing on identity, but must guess on row content and vocabulary reconciliation.

## Check results

### 1. UX-DR traceability — adequate

All 52 UX-DR rows resolve to real spec content and the summaries are broadly faithful. But the "Source Section" column is free text, not heading text: about 12-15 values match a heading exactly or nearly (e.g., UX-DR1 "Design system foundation" → `## Design System Foundation` line 265; UX-DR46 → `### Accessibility Microcopy Rules` line 1448), another dozen point at a heading under a different name (UX-DR34 "Governance form safety" → `### Form Patterns` line 1277; UX-DR50 "Responsive/accessibility matrix" → `### Testing Strategy` line 1478), and roughly 25 are invented labels naming bullets, inline list labels, or paragraphs (UX-DR3 "Trust as a contract" → bullet at spec line 124; UX-DR7 "Evidence cues" → bullet at line 335; UX-DR13 "Trust component contracts" → paragraph at line 359). Several are ambiguous among multiple locations — see findings. Summary fidelity exceptions: UX-DR17 names only 4 of the spec's 8 trust primitives and uses a name ("SafeReason") the spec never uses; UX-DR18 and UX-DR30 use shortened or coined names (details in findings).

### 2. Acceptance-criteria identifiers — strong

Exact, ordered, one-to-one parity holds. The spec defines precisely 28 identifiers, each exactly once: AC-SAFE-001..008 under `### Safety Acceptance Criteria` (spec lines 1325-1332) and AC-RESP-001..015, AC-A11Y-001..002, AC-LEAK-001, AC-MOB-001, AC-PERF-001 under `### Responsive Acceptance Criteria` (lines 1512-1531). The map inventories the same 28, in source order, with accurate Source Section values (the A11Y/LEAK/MOB/PERF IDs really are defined inside the Responsive Acceptance Criteria section). This matches Story 8.1's AC-8.1-04 frozen inventory (epics.md line 2589) and Story 8.2's 52/28 denominator (AC-8.2-01, line 2627). All 28 are phrased testably (observable state, scannable surfaces, explicit gates). No identifier appears in the map but not the spec, or vice versa. Caveat: two unnumbered acceptance sets exist outside the identifier scheme (finding 6).

### 3. Decision commitment — adequate

No "TBD", "to be decided", "open question", or "[ASSUMPTION]" markers exist, and the big decisions are genuinely committed: design system (FrontComposer + Fluent UI Blazor, spec line 269), chosen direction (Split Investigation Lens, line 798), breakpoints (lines 1403-1406), WCAG 2.1 AA (line 1424), mobile read-only default (line 1397), v1 read-only scope with named v1.1 deferrals (line 972). Conditionals are mostly safe defaults-with-escape-hatch ("standard Fluent UI breakpoints unless implementation evidence shows a need", line 1401). The silent ambiguities that remain are real but bounded: the "or equivalent" trust contract (finding 5), the generated-vs-custom search boundary stated both ways (finding 4), the freshness taxonomy conflict (finding 1), and unmarked normative force (finding 8).

### 4. Extraction ergonomics — thin

An AI agent given only map + spec can produce the 8.1/8.2 identity and ordering deliverables without full reads: the map is a complete, ordered 52/28 index; AC IDs are unique grep targets; disposition status and historical mappings are per-row columns; the hash/owner binding deferral is explicitly flagged (map lines 21-23). But it cannot produce the disposition rows without reading and interpreting the spec at large, because (a) the schema's required per-row `rationale`, `evidenceOrControl`, `compatibility`, and `disclosureSafety` fields (epics.md lines 2567-2569) have no source in either artifact (finding 2), and (b) the Source Section labels frequently do not resolve to a unique heading (finding 3). Anchor stability is also imperfect: the spec has two H2 sections effectively named "Core User Experience" (lines 76 and 410) with near-duplicate children ("Defining Experience" line 78 vs "2.1 Defining Experience" line 412), and a numbering scheme (1.1, 2.1-2.5) applied to only two of twelve H2 sections. There are no anchors, IDs, or line references anywhere in the map.

### 5. Contract fit with FrontComposer — strong

The spec expresses its UI intents in exactly the terms project-context.md mandates: generation from "annotated Conversations contracts and projections" (spec line 300), custom components only where trust interpretation demands it with a stated minimum-viable rule (line 315), no client-side trust inference (lines 317-319, AC-SAFE-005), command gates bound to server command availability metadata (lines 1034, 1050) matching project-context's contract-first annotation rule (project-context.md line 62), no tenant/user identity in forms (spec lines 1279-1280 mirroring project-context.md line 64), no raw EventStore browsing (spec line 321 mirroring project-context.md line 65), and generated/custom drift checks (line 1079). Architecture agrees (architecture.md lines 472, 552, 905-912). Friction points: the generated/custom boundary for search is stated both ways (finding 4), and the spec never maps its trust metadata concepts to FrontComposer annotation capabilities — acceptable at UX-spec altitude, but the named contract concepts it does offer are themselves unreconciled (finding 5).

### 6. Cross-artifact glossary — thin

Same concept, different names, in multiple load-bearing places: freshness states (spec vs architecture vs spec-internal, finding 1), the record-level trust summary (four names in the spec plus a fifth framing in the map, finding 7), the core loop (two AC-level names, finding 10), trust contract models (finding 5), and map-coined component/state names (finding 9). Consistent terms worth noting positively: "degraded hydration", "preserved-not-activated", "Leak Sentinel", "trust posture", tenant fail-closed language, and the redaction/unavailable/restricted microcopy distinctions (spec lines 1450-1456) are used consistently across spec, map, architecture, and project-context.

## Findings

- **high** Freshness vocabulary is split across the contract boundary. The spec's freshness taxonomy is `current, possibly-stale, stale, unknown, conflicting` (spec lines 1096-1102; Freshness Marker tests line 1033), while architecture mandates "one shared enum or value contract across API, UI, diagnostics, and evidence" (architecture.md line 1129) and enumerates `Current, Stale, Rebuilding, Unavailable, Forbidden, Redacted` (line 1211) and "current, stale, rebuilding, unavailable, and hidden-by-tenant" (line 977). The spec itself also uses "rebuilding" as a visible state (lines 331, 1043, 1048) yet excludes it from its own taxonomy. A dev implementing the shared enum must reconcile three sets alone. *Fix:* record the canonical enum (or an explicit spec-to-architecture mapping) in the UX-DR22/UX-DR29 disposition `rationale` fields during Story 8.1 execution; the spec bytes stay untouched.
- **high** The map's columns cannot populate the Story 8.1 disposition row schema without invention. Each of the 80 rows requires `owner`, `rationale`, `sourcePath`, `sourceSha256`, `evidenceOrControl`, `compatibility`, and `disclosureSafety` (epics.md lines 2567-2569). The map supplies id, status, and historical mapping per row plus one global owner; the hash/owner deferral is flagged (map lines 21-23), but `rationale`, `evidenceOrControl`, `compatibility`, and `disclosureSafety` have no declared source in any artifact — the 8.1 implementer must author them from scratch for 52 decisions and 28 criteria. *Fix:* add these as map columns (or a companion table) before hash binding, or declare constant/default values per field class in the 8.1 story contract.
- **medium** Non-resolving and ambiguous Source Section labels. UX-DR2 "Core experience / component strategy" spans two same-named H2s (spec lines 76, 410) plus `## Component Strategy` (line 974); UX-DR28 "Canonical fixtures" matches two distinct fixture lists ("Canonical trust-state fixtures" line 1175 and "Canonical safety fixtures" line 1348); UX-DR51 "Leak Sentinel" content appears in both `### Quality Gates` (line 1346) and `### Testing Strategy` (line 1508); UX-DR4, DR6, DR21, DR30 name content spread across three or more sections. *Fix:* normalize the map's Source Section values to exact heading text (optionally heading + line span) before Story 8.1 freezes the source hashes.
- **medium** The generated-vs-custom boundary for search is stated both ways. "Generated-first surfaces: Conversation search and filtering" (spec lines 340-341) versus custom composites "Tenant-scoped Find Pane" and "Trust Preview Result Row" (lines 1042-1043) and "customize only the search/result preview ... components" (line 825). A FrontComposer implementer must decide which parts of search are generated. *Fix:* record the intended split (generated search/filter chrome, custom trust-preview result rows) in the UX-DR11/UX-DR12/UX-DR18 disposition rationale.
- **medium** Two overlapping trust contract models, neither committed. "Recommended contract concepts" `TrustPosture`/`EvidenceItem`/`CommandAvailability` (spec lines 247-251) versus shared "`EvidenceTrustModel` or equivalent" (lines 999, 1137); no statement of subsumption, and architecture names neither. "Or equivalent" leaves the binding contract name open for the component layer. *Fix:* name the binding model in the UX-DR19 rationale, or record it there as an explicitly open architecture decision with an owner.
- **medium** Unnumbered acceptance sets sit outside the 28-ID denominator. "Design System Acceptance Criteria" (spec lines 361-369, 7 bullets) and "Component acceptance criteria" (lines 1109-1119, 11 bullets) are testable obligations with no identifiers; a consumer keyed to the enforced 52/28 inventories (epics.md AC-8.1-03/04) will not surface them, and no UX-DR summary enumerates them individually. They survive only via the whole-file hash. *Fix:* add a map note declaring which UX-DR rows carry them (UX-DR1/UX-DR13/UX-DR16 are the nearest owners), or assign identifiers in a future authorized spec revision.
- **medium** The record-level trust summary has four unreconciled names: "Trust posture summary" (spec line 225), "Trust Banner" (line 514), "Trust Posture Strip" (lines 818, 997, 1045, 1150), and "trust summary band" (lines 1265, 1367, 1413). The Merged component decisions list (lines 1055-1060) reconciles four other components but not these; map UX-DR32 uses "Trust summary band". *Fix:* one reconciliation sentence in the UX-DR32 disposition rationale naming the canonical component.
- **medium** Normative force is unmarked: 124 "should" vs 101 "must" occurrences with no convention note, sometimes inside one paragraph (e.g., spec line 755: redacted content "must be absent from DOM text ..." beside placeholders that "should preserve layout"). Obligation extraction cannot distinguish binding from advisory. *Fix:* a one-line convention in the map ("must = binding obligation; should = preserved design intent") — non-activating and cheap before freeze.
- **low** Map-coined names the spec never uses: "SafeReason" (UX-DR17) vs `SafeReasonInline`/`SafeReasonDetail` (spec lines 1030-1031); "Find Pane"/"Trust Preview"/"Governed Header"/"Evidence Timeline" (UX-DR18) vs "Tenant-scoped Find Pane"/"Trust Preview Result Row"/"Governed Record Header"/"Evidence Timeline Entry"; "no-access" state (UX-DR30) vs the spec's "denied"/"restricted"/"no accessible matches". UX-DR17 also lists 4 of 8 primitives, silently narrowing the preserved set for anyone acting from the summary. *Fix:* align UX-DR17/DR18/DR30 summaries to exact spec names, and either list all 8 primitives or say "all eight primitives in the Custom Components table".
- **low** Two canonical loop names at AC level: AC-RESP-005 and AC-A11Y-002 test "Find -> Read -> Trust" order while the component acceptance criteria (spec line 1111) and UX-DR25 use "Find -> Open -> Verify -> Cite, Act, or Stop". The equivalence is inferable from spec lines 88 and 416 but never stated where the tests are defined. *Fix:* equivalence note in the UX-DR25 rationale.
- **low** `ux-design-directions.html` sits outside the preservation contract: AC-8.1-02 fixes the source inventory to exactly spec + map (epics.md line 2587), yet the spec cites the HTML as decision provenance (spec line 785). The HTML carries no preservation-only banner, and its "Recommended base" badge (html line 682) covers two directions ("Case File Console and Split Investigation Lens", line 681) while the spec commits to one (line 798). Drift or deletion of the HTML is invisible to the 8.2 validator; a consumer opening it alone could read the wrong decision. *Fix:* annotate in the map that the HTML is non-canonical exploration provenance and the spec's Chosen Direction section is authoritative; optionally add the HTML to the source inventory via authorized change.
- **low** Authority-stamp skew across the pair: spec frontmatter carries `ux-preservation-planning-2026-08-01-v1` (spec line 32) while the map carries `ux-preservation-planning-2026-08-04-v3` and epic/architecture authority v12 (map lines 2-7), and the v9 story contract 8.1 binds authority v10 (`v9/story-contracts/8.1.json`); v13/v14 authority files also exist in the folder. The map self-declares the rebinding ("rebound by Epic 8 under v12", map line 23), but a consumer must trace sprint-change proposals to confirm the governing chain. *Fix:* have the Story 8.1 disposition's authority block restate the full current chain, and add a map note that its stamp supersedes the spec's frontmatter stamp.

Finding totals: 0 critical, 2 high, 6 medium, 4 low.
