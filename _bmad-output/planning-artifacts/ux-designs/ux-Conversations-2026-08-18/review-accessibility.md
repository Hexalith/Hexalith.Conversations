# Accessibility Review — Conversations UX preservation set

Reviewer lens: accessibility (WCAG 2.2 AA anchor) — BMad UX validation run, 2026-08-18.
Targets reviewed without modification:

- `_bmad-output/planning-artifacts/ux-design-specification.md` (read in full, 1,567 lines)
- `_bmad-output/planning-artifacts/ux-requirement-map.md`
- `_bmad-output/planning-artifacts/ux-design-directions.html` (concrete color values computed)

## Overall verdict

For a planning artifact, this spec commits an unusually deep accessibility floor: accessibility is framed as part of the trust model rather than polish, every load-bearing trust state has a committed non-color treatment with a named component and fail-closed states, and the redacted-vs-missing-data distinction — the hardest screen-reader problem on this surface — is explicitly solved with a microcopy taxonomy and a dedicated fixture. Two structural gaps keep it below a current-standard commitment: the floor is pinned to WCAG 2.1 AA (not 2.2 AA) in all three places it appears, and the mechanism by which a disabled governance action exposes its blocked reason to keyboard and screen-reader users is never specified, even though disabled buttons are unfocusable and silent by default — the exact failure that would make a governance action unusable. The direction mocks pass AA text contrast on all five status treatments, but with almost no headroom and with the token values never bound into the spec.

## Check results

### 1. Stated floor — adequate

The floor is explicit, repeated, and scoped: "The target accessibility baseline is WCAG 2.1 AA for operator/admin web surfaces" (spec line 1424), "WCAG 2.1 AA contrast for text, status labels, controls, and timeline markers" (line 744), and automated testing pinned to "WCAG 2.1 AA issues" (line 1499). UX-DR44 in the requirement map preserves it as a durable decision. Keyboard completeness (AC-RESP-005, line 1516; component AC line 1111), screen-reader parity (line 1424), and focus management (drawer trap/return lines 1430–1431, AC-RESP-013) are all first-class. The deduction: the declared level is 2.1 AA in a 2026 spec judged against 2.2 AA — see finding 1. The floor exists and is enforceable; it is simply one standard revision behind.

### 2. State perceivability — strong

Every core state has a committed, named treatment, not intent-level prose:

- **Trust states:** Trust Posture Strip — "every state has visible text and screen-reader text; color is never the only signal" (line 1045); Visual Trust Invariant — "Every status must combine label, icon or shape, accessible text, deterministic state source, and optional color. Color is supplemental." (line 630).
- **Freshness/staleness:** Freshness Marker primitive with a five-value taxonomy (current / possibly-stale / stale / unknown / conflicting, lines 1096–1102) plus required timestamp, source, and version inputs (line 1033); missing metadata renders "unknown and suppresses confidence".
- **Denial/blocked:** Command Gate with enumerated states and "blocked reasons visible without hover" (line 1050); SafeReasonInline primitive (line 1030).
- **Degraded hydration:** Participant Identity Marker with unresolved/permission-filtered/stale-hydration states and identity-dependent command blocking (line 1036).
- **Redaction:** Redaction Placeholder — "semantic, not cosmetic" (line 1432), forbidden raw content inputs, layout-preserving placeholder that does not expose value length (line 755).

"No status may rely on color alone" appears as a hard guardrail (line 375) and again per state family; grayscale and high-contrast review is required for all statuses (line 751). Contrast targets are stated (AA, line 744) but only generically — the named domain tokens (`--conversation-status-verified` etc., lines 729–734) carry no values, so the committed treatments have no committed numbers (finding 4). Icon/shape-per-state mapping is required in principle but never enumerated.

### 3. Announcements & live updates — adequate

The strongest element in the whole document is the screen-reader distinguishability of redaction from absence: the Accessibility Microcopy Rules (lines 1449–1456) define "Redacted" (content exists, cannot be seen), "Unavailable" (existence unconfirmed), "Restricted" (denied by policy), "Still loading", and "Some events unavailable" as distinct, consistently used state words, backed by the `AssistiveTech_RedactionAnnouncement` fixture (line 1543) and AC-A11Y-001 accessibility-tree verification. A screen-reader operator can tell a redaction notice from missing data — this check's hardest question is answered.

Change announcement is thinner: the entire live-update contract is one sentence — "Trust state changes, projection freshness changes, command availability changes, and permission downgrades should be announced through appropriate live-region behavior" (line 1434) — with no politeness levels, no rebuild-complete announcement, no focus policy when content is replaced mid-read, and "should" rather than "must". Only permission downgrade gets an acceptance criterion (AC-RESP-006). See finding 3.

### 4. Keyboard & focus — adequate

Breadth is excellent: keyboard access is enumerated for search, filters, result selection, timeline navigation, citation copy, drawer open/close, command gates, and confirmation dialogs (line 1561); keyboard-only completion of the full Find → Open → Verify → Cite/Act/Stop loop is an acceptance criterion three times over (lines 752, 1111, AC-RESP-005). Focus order is defined to follow the trust workflow (line 1429), drawers trap and return focus only after authorization (lines 1430–1431), virtualized timelines must preserve keyboard navigation and focus restoration (line 1466), and AC-RESP-013 governs focus landing after navigation and modal close.

The gap is mechanism-level and sits exactly on the trust-critical control: the spec commits the outcome ("Disabled actions expose reason text without requiring hover", line 747; "A screen reader user hears … blocked-action reasons", line 1112) but never says how a disabled Command Gate is reachable — no `aria-disabled`-focusable pattern, no programmatic association (e.g., `aria-describedby`) between control and reason. Native/Fluent `disabled` buttons are removed from the tab order and announce nothing (finding 2). Temporal-cursor navigation, though named as a custom trust-critical surface (lines 819, 1044), never appears in any keyboard-access enumeration (finding 9).

### 5. Fluent UI inheritance — adequate

The inheritance boundary is explicit and well-policed at the category level: Fluent UI Blazor owns "forms, inputs, validation summaries, buttons, icon buttons, menus, tabs, dialogs, drawers, badges, lists, grids, tables, pagination, filters, loading states, empty states, and focus behavior" plus "theme tokens, typography primitives, density controls, disabled states, keyboard behavior, and accessibility foundations" (lines 985–986), and "Use semantic HTML and Fluent UI accessibility primitives before adding ARIA manually" (line 1559). Crucially, the spec does put obligations on exactly the custom components where inherited accessibility does not come free: "Custom components must declare their projection inputs, command metadata inputs, fail-closed behavior, accessibility behavior, degraded-state behavior, and tenant-isolation test coverage" (line 359), plus per-primitive accessibility test expectations in the primitives table (lines 1027–1036) and automated accessibility coverage for all trust surfaces (line 369).

Two weaknesses: no specific Fluent component or variant is ever named (no FluentDataGrid/FluentDialog-level mapping), so "Fluent's accessibility for free" is asserted at the family level only; and the 5.0.0-rc.2 release-candidate status of the baseline is never acknowledged as an accessibility risk — an RC's "accessibility foundations" are an unvalidated inheritance assumption (finding 6).

### 6. Direction mocks — adequate

All five semantic status-chip text treatments in `ux-design-directions.html` pass AA 4.5:1 for normal text (chips render at 11px, so the 4.5:1 bar applies), but verified and warning pass with under 0.3 of headroom. The disabled-button treatment — used in the mocks to carry the blocked reason itself ("Redact blocked", html line 732) — computes to 4.09:1, below 4.5:1; WCAG 1.4.3 exempts inactive components, but the spec's own commitment makes that label load-bearing. Control boundaries drawn with `--line` (#d4dbe4) on white compute to 1.40:1, below the 3:1 non-text minimum (1.4.11) for boundaries that identify a component (the search input, html lines 231–242). Full table below.

### 7. Regulated-language surfaces — thin

Plain-language and non-blaming commitments are real: "Negative states should use precise, non-alarming language" (line 149), "Fail closed, explain calmly" (line 120), business-safe vocabulary mandated over CI jargon (line 183), permission-safe denial copy patterns ("No accessible records match this query", line 833), consistent state words (lines 1449–1456), reason codes paired with short user-facing explanations (SafeReasonInline, line 1030), and waiver/blocker labels "readable outside developer context" (line 1053). What is entirely absent is localization: no occurrence of localization, i18n, or translation-of-locale anywhere in the spec or map. The reason-code-plus-explanation pattern is localizable by construction, but nothing commits messages to a localizable catalog, and the load-bearing semantic distinctions of the microcopy taxonomy (Redacted ≠ Unavailable ≠ Restricted) are defined only as English strings with no requirement that they survive translation (finding 5).

## Findings

- **[high]** The accessibility floor is pinned to WCAG 2.1 AA, not 2.2 AA, in all three normative locations (spec lines 744, 1424, 1499) and preserved as such by UX-DR44 (ux-requirement-map.md line 72). For a 2026 trust-critical governance surface this leaves 2.2-only AA criteria formally untested: Focus Not Obscured (2.4.11) is directly load-bearing given the spec's sticky trust summary bands, persistent headers, and drawers over a focused timeline; Target Size Minimum (2.5.8) applies to all pointer input while the spec's 44px commitment is conditioned on "where touch operation is supported" (line 1435); Redundant Entry (3.3.7) touches the rationale-driven governance forms. Because automated checks are scoped to "WCAG 2.1 AA issues", a UI failing current AA would pass every committed gate. *Fix:* Rebaseline all three statements and UX-DR44 to WCAG 2.2 AA; add an explicit Focus Not Obscured obligation for sticky trust bands/drawers and an unconditional 24x24 minimum target size.
- **[high]** Blocked-action exposure has a committed outcome but no committed mechanism (spec lines 747, 1050, 1112). Disabled buttons are unfocusable and silent to sequential keyboard/screen-reader navigation by default, so "reason text without requiring hover" is unreachable for exactly the users the spec protects; the direction mocks reinforce the trap by carrying the reason as the disabled button's own label (`<button class="button disabled">Redact blocked</button>`, html line 732) in a treatment WCAG exempts from contrast because it is inactive. Downstream impact: a keyboard or screen-reader operator cannot discover why a governance action is blocked — an unusable governance action and a possible wrong inference that the action does not exist. *Fix:* Commit the pattern: blocked Command Gates remain focusable (`aria-disabled="true"`, not `disabled`), the safe reason is programmatically associated via `aria-describedby`, and the adjacent visible reason text meets 4.5:1 independently of the control's disabled styling; add this to the Command Gate row and the accessibility test list.
- **[medium]** Live-update announcement is intent-level: one "should" sentence covers all trust, freshness, command-availability, and permission changes (line 1434), with no politeness levels, no announcement for projection rebuild completion or stale→current transitions, no focus/announcement policy when redaction replaces content the operator is reading, and no toast-vs-live-region channel decision (toasts appear only in leak rules, lines 1458, 1558). Only permission downgrade has an AC (AC-RESP-006). Downstream impact: a screen-reader operator can keep relying on a view that silently went stale — the exact "no silent confidence" failure the spec forbids (line 123, failure mode line 759). *Fix:* Specify per state-change class: live-region politeness (freshness/staleness = polite; command-availability loss and redaction-in-place = assertive), required announcement copy pattern (state word + next safe action, per line 1444), and add stale-transition and redaction-replacement announcements to the acceptance criteria.
- **[medium]** Contrast targets are declared but never bound to values: the domain semantic tokens are named without colors (lines 729–734), "WCAG 2.1 AA contrast" is asserted generically (line 744), and the only concrete values live in the non-normative direction mocks, where the two most safety-relevant treatments pass with almost no margin (verified 4.74:1, warning/stale 4.78:1 at 11px). Downstream impact: any implementation-time token drift (theming, dark mode, Fluent alias remap) silently drops the freshness and trust treatments below AA with no spec-level check to catch it. *Fix:* Bind minimum contrast ratios (and the mock hex values as reference implementations) to each `--conversation-status-*` token in the spec, require ≥4.5:1 at the rendered chip size in both themes, and add a token-level automated contrast test to the quality gates.
- **[medium]** No localization commitment for regulated microcopy: the denial/redaction/audit state words and safe-reason explanations are defined only as English strings (lines 1449–1456, 833, 1030), with no i18n/localization requirement anywhere in the spec or requirement map. The taxonomy's semantic contrasts (Redacted ≠ Unavailable ≠ Restricted) carry governance meaning that must survive translation. Downstream impact: a translated deployment can collapse the redacted/unavailable distinction and mislead operators about whether content exists. *Fix:* Add a microcopy rule requiring reason codes + localizable message catalog keys (never hard-coded strings) for all safe-state words, with a translation acceptance check that the five state words remain pairwise distinct in every supported locale.
- **[medium]** Fluent UI inheritance is category-level and the 5.0.0-rc.2 baseline's release-candidate status is never acknowledged as an accessibility risk (lines 978–989, 1315–1321). No component/variant is named, so "focus behavior, disabled states, keyboard behavior, and accessibility foundations from Fluent UI" is an unvalidated assumption for dialogs, drawers, grids, and tabs at RC quality. Downstream impact: teams treat inherited surfaces as accessibility-done and skip verification exactly where the spec provides no custom obligations. *Fix:* Add a component inventory mapping each generated surface to the named Fluent component and require a one-time accessibility conformance smoke (keyboard + SR) of the inherited components at the pinned Fluent version before the generated-first surfaces are accepted.
- **[low]** In the direction mocks, component boundaries drawn with `--line` #d4dbe4 on #ffffff compute to 1.40:1, below the 3:1 non-text contrast minimum where the boundary identifies the control — most notably the search input (html lines 231–242) and result-row cards; status-chip borders (#a9d9bf, #efd08a ≈1.4:1 against chip fills) are decorative since text carries the state. *Fix:* Note in the spec that mock border values are non-normative and require 3:1 boundaries for inputs and interactive rows (or rely on Fluent's compliant field styling explicitly).
- **[low]** The mocks label redactions with the bare code "R2" as the entire chip text (html lines 848, 988, 1046), which a screen reader announces as "R2" with no meaning — conflicting with the spec's own requirement that visible text carry the state (line 1249). As the concrete reference treatment, this invites terse-code shipping. *Fix:* Show the committed pattern in mock-equivalent fixtures: visible "Redacted" word plus code, with the accessible name reading the full state ("Redacted — policy R2").
- **[low]** Temporal-cursor navigation is a named custom trust-critical surface (lines 313, 819, 1044) but is absent from every keyboard-access enumeration (lines 745, 970, 1561) and has no focus-management rule for cursor moves (which re-render the timeline — a focus-loss hotspot). *Fix:* Add temporal cursor operation to the keyboard-access list and specify focus behavior after a cursor jump (land on the trust summary region per AC-RESP-013).
